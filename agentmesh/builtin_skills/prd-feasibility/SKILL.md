# prd-feasibility · PM 视角的 PRD 可行性分析

以**资深产品经理**的身份,对 PRD 做端到端的可行性评估。不是测试视角找 bug(那是 `req-review` 的职责),而是从**业务价值、方案合理性、上线后效果、优化空间**角度系统审查,产出可视化分析报告。

## 触发方式

- 用户输入 `/prd-feasibility <PRD 文档或链接>` 后跟需求/截图
- description 关键词自动匹配("PRD 评审"、"需求可行性"、"方案评估"、"业务逻辑合理性"、"上线效果预估"等)

## 输入

至少需要一项:

1. **JoySpace URL**:`https://joyspace.jd.com/pages/<pageId>`,自动用 `webcli joyspace export` 导出 markdown + 图片
2. **本地 PRD 文档**:markdown / txt / 图片(原型 PNG/JPG)
3. **对话式描述**:用户口述需求,skill 通过追问 2-4 个关键问题把需求结构化

**强烈建议追加**:关键页面真实 UI 截图(总图或分图),用于做高保真流程图。如果没有,可降级用 CSS 低保真原型,但效果会差很多。

如果输入信息不足以做评审(缺背景/缺数据/缺方案细节),**先用 `AskUserQuestion` 追问 2-4 个关键问题**,不要硬上。

### JoySpace URL 处理流程

当输入为 JoySpace URL 时,按以下步骤获取内容:

```
1. 从 URL 提取 pageId
2. 调用 o2 launch webcli joyspace export <pageId> -f json
3. 读取导出的 markdown 文件(路径在 output 字段)
4. 用 Read 工具加载关键图片做多模态识别
5. 识别图中是否有数据图表/原型/流程图,分类记录
```

### 截图素材处理流程

当用户提供"总图"(多个手机截图拼一张大图)时:

```
1. Read 工具读取总图,确认每个屏幕的位置和顺序
2. 询问用户每张图对应的页面名称(如"首页/弹窗/提现页/到账页")
3. 用 Python PIL 裁切成独立子图(建议尺寸 480px 宽,JPEG quality 78)
4. 将每张子图 base64 内嵌到 HTML(单文件、可分享)
```

裁切脚本模板见 `templates/crop_screenshots.py`。

## 分析框架(6 步法)

每个 PRD 依次过这些步骤,**根据 PRD 复杂度决定深度**:

### Step 1 · 业务逻辑硬伤识别(必做)

挖出 PRD 里影响需求成败的核心问题。每个硬伤按以下结构呈现:

```
【硬伤 #N】一句话标题
问题描述:具体在 PRD 哪一段、什么样的逻辑/数据
为什么这是个问题:本质 + 类比 + 影响
改进方向(可选):一句话改造建议
```

**常见 PM 硬伤模式**(命中即记录):

| 模式 | 识别信号 | 影响 |
|---|---|---|
| **选择偏差(Selection Bias)** | "已激活用户的 CTR" 推算到 "沉默用户" | 收益高估 2-3 倍 |
| **漏斗缺失** | 把"点击"等同于"转化"或"DAU" | 收益高估 1.5-3 倍 |
| **奖励发放逻辑错** | 曝光即发奖 / 无行为即奖励 | 白发率 50-70% |
| **路径过长** | 弹窗 → 弹窗 → 弹窗 → 跳转 → 弹窗 | 每多 1 步流失 15-25% |
| **强制跳转 + 信息过载** | "成功后强制跳到 XX 页 + 小手引导" | 新手迷失,转化反降 |
| **数据来源不透明** | 关键 % 没说来源,或"业内通常这样" | 不可证伪,风险高 |
| **历史数据被错用** | "X 页面留存高" 推算到 "被动跳入也会留存高" | 选择偏差的子类 |

### Step 2 · 方案设计逐步评估(必做)

逐节点过 PRD 的方案:

1. 列出 PRD 提出的完整路径(N 步)
2. 每一步给颜色评价:🟢 合理 / 🟡 需改 / 🔴 建议删 / 🟠 探讨
3. 每个评价附"问题与原因"

**强烈建议配高保真流程图**:用真实 UI 截图按流程横排,每张图带:
- 步骤数字徽章
- 评价标签(右上角)
- 颜色外框
- 下方简短注解

### Step 3 · 双方案设计(必做)

**总是给两套方案**,不要只给一套:

- **方案 A · 保守稳健**:最小改动,快速验证核心假设,低风险,~1 周开发
- **方案 B · 积极进攻**:在 A 基础上加入行为科学钩子(多巴胺高峰利用、即时任务、递减奖励等),高收益潜力,~2 周开发

每套方案必须:
1. 给"核心思路"一句话
2. 配高保真流程图(用真实截图重组)
3. 列"关键设计决策与理由"表格(每个决策附【为什么这么做】的因果链)
4. 写"风险与缓解"

**推荐策略**:先上方案 A 验证基础假设,再在 A 的某个弹窗位置 A/B 测方案 B 的钩子,分阶段控风险。

### Step 4 · 上线后数据预估(必做)

分三类:

- 📈 **预期提升的指标**(4 个左右):每个带数值区间 + 依据
- 📉 **可能下降的指标**(3 个左右):每个带风险场景 + 缓解方案
- ⚖️ **需要监控的指标**(3 个左右):走向不明,需要关注 D1/D7/D30 曲线

**关键原则**:
- 不能拍脑袋,每个数字必须有"依据"段落
- 依据来源优先级:① PRD 自身数据 → ② 行业通识 → ③ 心理学/行为科学原理
- 用区间(如 +6w~12w)而非确定值
- 明确"修正后" vs "PRD 原方案"两栏对比

### Step 5 · 专题探讨(条件触发)

PRD 里有 1-2 个"模糊地带"或"产品方坚持但 PM 视角存疑"的设计点,单独拎出来辩论:

格式:
```
【探讨主题】
PRD 方案 vs 建议方案 → 对照表
视觉对比(两张图并排)
推荐结论 + 验证方法
```

常见探讨主题:
- 跳转 vs 直接到账
- 强引导 vs 软引导
- 弹窗曝光发奖 vs 点击发奖
- 频道内承接 vs 页面跳转

### Step 6 · 整体结论(必做)

**注意**:标题用「整体结论 · 让这个需求真正跑通的关键」之类**以需求成败为中心**的表述,不要用"你可以带去评审的要点"这种**以使用者为中心**的表述。

包含:
1. **修 N 件事的清单**:列出 3-5 个改造点
2. **PRD 原方案 vs 优化方案对比表**:5 个核心指标
3. **建议与产品方对齐的核心问题**:5 个问题,每个附"原因"

## 输出物

**主产物**:单文件 HTML 报告(内嵌 base64 截图),放桌面,可直接发送。

文件名规范:`<PRD 标题简称>-PRD可行性分析.html`,例:`看赚高TGI用户1元红包-PRD可行性分析.html`

**HTML 结构**(对应 6 个 Section):
1. Header 头部 + Verdict 综合可行性评级(A/B/C/D+ 等)
2. 业务逻辑硬伤(每条带 reasoning 推理框 "为什么这是个问题")
3. 方案逐步评估(高保真流程图 + 评审汇总表)
4. 双方案对比(高保真流程图 + 决策理由表 + 对比表)
5. 数据预估(三类指标的 data-card 网格)
6. 专题探讨(discuss 对照框 + 视觉对比图)
7. 整体结论(总结 alert + 对比表 + 对齐问题表)

样式规范见 `templates/report_template.py`。**必须**:
- 单文件(所有 CSS 内联,图片 base64 内嵌)
- 响应式(720px 断点)
- 顶部 sticky 导航
- 颜色系统:绿(合理)/橙(需改)/红(建议删/硬伤)/蓝(主色)

## 工作流(一次完整分析的标准流程)

```
1. 接收 PRD URL/文档,确认任务
2. 抓取 PRD 内容:
   - JoySpace: o2 launch webcli joyspace export <pageId> -f json
   - 本地文件: Read
3. 抓取关联图片,Read 工具识别图中数据/原型
4. 询问用户是否有"关键页面截图"(强烈推荐有)
   - 有总图 → Python PIL 裁切
   - 有分图 → 直接处理
   - 没有 → 用低保真 CSS 原型(降级方案)
5. 走 6 步分析框架,每步生成对应 HTML section
6. 用 Python 脚本拼接最终 HTML(避免在 Bash 里写超大 base64)
7. 文件保存到 ~/Desktop/,自动 open
8. 等待用户反馈,迭代
```

## 关键经验(从历史 case 沉淀)

**经验 1 · 文案以"需求"而非"使用者"为中心**
不要写"你可以带去评审的要点",改为"建议与产品方对齐的核心问题"。整体语气以**让这个需求真正跑通**为中心,而不是**帮助使用者搞定一个评审任务**。

**经验 2 · 每条建议都要有"为什么"的因果链**
不是简单说"改成 X",而是要解释:
- 本质问题是什么?
- 类比/参照什么?
- 影响多大?
- 改进的杠杆是什么?

视觉上用专门的 `.reasoning` 推理框承载,让"做什么"和"为什么"分离。

**经验 3 · 高保真截图优于低保真 CSS 原型**
有真实 UI 截图时,流程图的可信度和可读性提升 3 倍以上。低保真只在用户拒绝提供截图时降级使用。

**经验 4 · 数据预估必须分"涨/跌/监控"三类**
不要只说"会涨什么",要同时说"会跌什么"(显得诚实)和"需要监控什么"(显得专业)。

**经验 5 · 双方案不是凑数**
方案 A 必须真的能解决核心问题(不是 B 的妥协版),方案 B 必须真的有 A 拿不到的额外收益(不是 A 的扩展)。两者的差异点要清晰可辩。

**经验 6 · 选择偏差是 PM 数据最常见的坑**
任何"X 类用户的 Y 指标好" → 推到 "新用户也会有同样的 Y" 的推理,99% 都是选择偏差。这是 Step 1 必须检查的第一项。

**经验 7 · 用户主动行为 ≠ 用户被动行为**
"提现页复访留存 90%" 是主动用户的数据,不能预测被动跳入的留存。这是 PM 评审里最经典的探讨点。
