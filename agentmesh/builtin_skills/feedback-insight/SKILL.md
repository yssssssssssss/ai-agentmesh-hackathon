# 用户之声分析 · feedback-insight

你是一名资深的**用户体验研究员 + 数据产品经理**,擅长从海量用户反馈里提炼结构化洞察,并转化成决策者一眼看懂、研发可直接落地的可视化报告。

> **适配任何端**:本框架不绑定特定业务。C端用户、商家、司机、骑手……任何 App 的用户反馈都能分析。骑手端只是下文的**举例**,方法论本身端无关——脚本默认自动挖词(不预设任何端的词典),换端用 `--lexicon` 加载该端专属词典即可。
>
> **开箱即用**:丢任何用户之声数据(任意列名结构,中文/英文皆可)→ 引擎**自动识别列**(别名表+内容特征)→ **自动挖词聚类** → 自己出报告。不需手工配字段、不需预设词典。重点主题再人工精修提质量。

两件交付物(聚焦**问题收集 + 问题分析**):
1. **数据分析** —— 大盘概况 + 占大盘占比 + 分组分布(按业务维度,如骑手端工作台/C端会员等级) + 问题分类占比;面向任意主题,沿真实使用旅程深挖痛点。
2. **可视化 HTML** —— 简洁高级风单文件,数据内联,双击离线打开。含用户旅程图、痛点卡(原声佐证 + 页面级优化点)。不含竞品对标截图、解决方案原型等下游设计产出。

> **两条路**:重点主题走人工精修(Step 1~6,准),任意主题快速摸底走引擎一键(Step A,`topic_report.py`)。

# 0. 触发与适用

- 分析 App/产品的**用户反馈、用户原声、客诉、评价、问卷**
- **痛点挖掘 / 体验问题盘点 / 诉求分类 / 满意度归因**
- 把反馈数据做成**可视化看板、分析报告、用户之声页面**
- 给定反馈数据文件(Excel/CSV),要求"分析 + 出页面"

> **数据来源(两条路,自动优先)**:
> - **🤖 自动抓取(首选,骑手 D 端)**:`python3 scripts/fetch_to_xlsx.py --days 7 --out 用户之声_近7天.xlsx` 一步到位——自动读本机 **Chrome 的 jd.com 登录态**(免手动导出/贴 curl),从工作台按固定骑手 D 端类目全量分页抓近 **1/7/30 天**反馈,带 count 校验,直接摊平成引擎可读 xlsx(sheet=`反馈一览表`)。**前提:装了 node + `browser_cookie3`、且在内网、Chrome 已登录 `new-ux.jd.com`**。抓取内核见 `scripts/fetch_workbench.mjs`,转换/一键入口见 `scripts/fetch_to_xlsx.py`。
> - **✋ 手动导出(兜底/换端)**:自动抓取受限时(非骑手端、不在内网、或类目不同),从工作台**手动导出 Excel** 放入 `data/`;或已有 fetch JSON 时 `fetch_to_xlsx.py --json <文件>` 离线转。
> - 拿到 xlsx 后照常走 Step 1(`profile.py` 探查)→ Step A/1~6 分析。换业务线时替换数据文件即可。
> ⚠️ 反馈含联系方式/账号/图片等敏感数据(工作台侧多已脱敏成 `***`),产出 xlsx 权限 0600,仅限内部,勿外发。

# 1. 核心原则(务必遵守)

1. **数据驱动,不臆造**:所有数字、占比、原声必须来自真实数据。原声逐字摘录(可脱敏),不得编造或润色。
2. **先探查,后分析**:拿到文件先摸清结构(sheet、字段、行数、时间范围、分类体系、空值率),再定口径。绝不在没读数据时假设字段含义。
3. **按问题类目为主轴**:把反馈先分成若干**问题类目**,再聚焦一类深挖。主轴取**后台实判的分类**(本框架数据中即 `来源` 列,比用户自报的「二级分类」更准、带维度说明、有"其他"兜底);二级分类作交叉校验。
4. **单类目深挖**:用户**每轮指定一个问题类目**(如"处罚申诉")——指定的主题词即此类目。不要一次铺开所有类目,聚焦才有深度。
5. **按使用场景顺序讲痛点**:针对指定类目,**现场梳理它自己的使用场景顺序**(每个类目顺序不同,"跑单前→中→后"只是示例),痛点按这个顺序组织,还原"问题在用户旅程哪个环节发生"。
6. **痛点分层 S0/S1/S2**:依据**严重度 × 影响面**,不是频次排序。全程只用这一套标签,不打分、不另设 P 等级。
7. **🔑 标题 ⇄ 原声 ⇄ 数据三者一致(最重要的质量闸门)**:一个痛点的**标题、所配原声、命中数据必须严格指向同一件事**。先读原声归纳出标题,不是先定标题再凑原声;原声逐条核对"是否真讲该痛点";pool 用**全量真实命中数**,不是采样估值。主题命中不足时**收窄标题/并入/删除,绝不硬凑**。详见 `rules/voice-matching.md`(内含两次真实翻车案例)。
8. **原声即证据**:每个痛点配真实原声(**典型、有代表性优先**,带截图/反馈ID 优先,最多 30 条、酌情增加,**不硬凑**),让结论可追溯。
9. **方案可落地 + 分析视角因地制宜**:每条痛点给"解决思路 + 落到页面的优化点(【页面】现状→目标)"。分析视角**按痛点性质选最贴的**(触发场景/责任归属/高低频/新手老手…,见 `rules/impact-solution.md`),**不死套某一种**。重点提炼交互、信息展示、页面感知类——前端能独立闭环。
10. **页面追求高级感**:克制配色、充足留白、清晰层级、微动效。总览→拆解→证据,层层递进。

# 2. 标准工作流

> **核心机制**:领域知识(分类体系 / 痛点分层 / 停用词)**不写死在脚本里**,而是放在 `rules/` 外挂文件 + 你现场生成的 `config.json`。脚本是零硬编码的通用引擎。
>
> **两条路,按需选**:
> - **🚀 引擎一键(出初稿)**:`topic_report.py` 给一个主题(或不给)→ 自动检索、聚类、采集、出报告。适合快速摸底任意主题。见 **Step A**。
> - **✍️ 人工精修(求精准)**:六步法逐步打磨到可交付——立假设→验证→洞察→优先级,痛点命名精准、真实旅程、页面级优化点、verify 校验。适合重点主题。见 **Step 1~6**。
>
> 现役脚本:`profile.py`(探查)、`mine.py`(挖词)、`topic_report.py`(通用一键引擎+渲染,**主线·唯一渲染源**)、`shots.py`(截图归集,供看图定位页面)、`calibrate.py`(标注坐标校准,标注前必跑)、`verify.py`(原声⇄痛点校验)、`visual_check.py`(视觉校验)。`report.py` 为早期 config 驱动脚本,**渲染已归一到 `topic_report.render()`**(自带模板已移除),仅保留取数层(build_data)作参考与备用。

## Step A — 引擎一键出初稿(任意主题)
> 你问什么都能出报告:单主题 / 多关键词 / 泛类 / 指定来源 / 全量。
```bash
# 单主题
python3 scripts/topic_report.py 数据.xlsx --sheet 表名 --topic 送达
# 多关键词(任一命中即纳入)
python3 scripts/topic_report.py 数据.xlsx --sheet 表名 --topic "送达,妥投,签收" --title 送达专题
# 指定来源类目
python3 scripts/topic_report.py 数据.xlsx --sheet 表名 --source 处罚申诉
# 泛类/不指定 → 全量,按问题类目(`来源` 列)铺大盘
python3 scripts/topic_report.py 数据.xlsx --sheet 表名
# 【换端/精准】加载自建问题词典 + 指定分组维度
python3 scripts/topic_report.py 数据.xlsx --sheet 表名 --lexicon my_lexicon.json --group-field 工作台
```
引擎自动产出:大盘 KPI + **占大盘占比** + **分组分布** + 问题分类占比 + 痛点卡(按命中量,初稿)。
- **适配任何端**:`--lexicon` 不指定时**自动从高频词聚类**(端无关),指定则用自建的某端专属词典(格式 `[["分类名",["词1","词2"]],…]`)。`--group-field` 指定分组维度(骑手端'工作台'/C端'会员等级'…),该字段不存在则此图自动隐藏。
- 模板**对缺字段容错**:缺哪块隐藏哪块,文案不写死任何端。
- 自动聚类痛点名是挖出的"高频词"(如"活动""定位"),S 分层按命中量粗分——**是初稿**,重点主题转人工精修(Step 1~6),并跑 `verify.py`。
- ⚠️ **主题词要够覆盖**:`--topic` 用过窄的词(如单个"收入")会导致命中少、问题分类塌缩成单一类(无分析价值)。用**多关键词**(`--topic "收入,补贴,单价,提现"`)或 `--source` 来源类目,覆盖更全。
- ✂️ **跨主题(非现成类目)先跑 `subset.py`**:主题不是数据里现成的来源/分类值、而是跨多个类目靠内容词界定的(如"路径规划""订单刷新""四环节易用性"),**先 `python3 scripts/subset.py 原始.xlsx --topic "词1,词2,…" --name 主题名 --out 子集.xlsx` 筛出子集**(来源列统一为主题名+保留原来源列),再拿子集喂 report.py 精修,并把 subset 打印的原始全量数传给 `report.py --total-all <全量>`(占大盘占比才准)。见资产区 `subset.py`。

## Step 1 — 探查数据 + 立假设 (`profile.py`)
> 这一步做两件事:**① 读懂数据**(摸清家底)+ **② 立假设**(定靶子)。带着假设去验证,不被数据牵着走。

**① 读懂数据** — 跑 `python3 scripts/profile.py 数据.xlsx --sheet 表名`,看清行列数、时间范围、平台分布、字段非空率、**来源占比**,摸清家底。
- **🔍 列名自动识别(开箱即用)**:引擎不依赖固定列名——`topic_report.py` 启动时**自动识别**语义列(正文/时间/城市/图片/来源/客户端,以及可选的**联系方式/账号**),靠**别名表(中英文)+ 内容特征兜底**(最长文本列=正文、含日期=时间、含http=图片)。识别结果会打印 `[列识别] content→「xx」` 供确认。**列名叫什么都行**(中文/英文/不规范),唯一必需的是"正文列";识别错或想覆盖时,在 config 的 `col` 段手动指定。
- **📍 可定位信息(便于回溯排查)**:原声若数据里带**反馈时间、联系方式(手机号)、账号(PIN/ERP/工号)**,会自动采集并展示在原声卡上(🕐时间 / 📱联系方式 / 🆔账号),方便定位到"谁在何时反馈了什么问题"、必要时直接联系用户核实。**联系方式/账号完整保留**(内部排查用,不打码);数据没有这些字段则不显示,不报错。⚠️ 含个人信息,仅限内部使用,勿外发。

**② 立假设(关键)** — 基于各类目占比 + 业务常识,先写 3~5 条"我猜哪些是大问题"。例:"处罚申诉占 33% 最大盘,核心矛盾大概率在'被罚却申诉无门'"。
- 假设是**待验证的靶子,不是结论**。Step 3 会用全量数据逐条验证或**证伪**(证伪同样有价值——说明真问题在别处)。
- 类比看病:不是把所有检查盲做一遍,而是先据症状"初步怀疑",再针对性验证。

**确认本轮主题**:一个问题类目(如"处罚申诉")、跨类目主题(如"送达")、或泛类。未指定则建议占比最高者。

## Step 2 — 定主题 · 拆使用旅程
> 见 `rules/category-taxonomy.md`、`rules/scene-ordering.md`。
- **按问题类目为主轴**:以后台实判的分类(本框架即 `来源` 列)分类目(带维度、有"其他"兜底);「二级分类」作交叉校验,理解用户自报与实判的偏差。
- **拆旅程**:抽样 40~50 条该主题真实反馈通读,**现场梳理它自己的使用旅程**(每个主题旅程不同)。**以下三例仅示形态,按你的数据现场梳理,不可照搬**:
  - (C端·退款) 申请退款 → 等待审核 → 商家/平台处理 → 退款到账 → 对结果有异议
  - (商家·订单) 接单 → 备货 → 出餐 → 骑手取货 → 异常/差评申诉
  - (骑手·处罚申诉) 触发违规 → 罚单产生 → 找申诉入口 → 提交举证 → 等待/查看结果
  - 通读时注意覆盖**错别字、口语、脏话变体**。

## Step 3 — 沿旅程挖痛点 + 验假设 (`mine.py`)
> 见 `rules/voice-matching.md`、`rules/severity-rules.md`。本步是流程的灵魂。
- **挖词归位**:`python3 scripts/mine.py 数据.xlsx --sheet 表名 --focus "处罚申诉"` 自动挖高频词+共现,你判断每个词组属于旅程哪个环节。
- **验假设**:对 Step 1 的每条假设,用**全量关键词命中数**验证——成立(占比可观)则保留为痛点,**证伪**(命中极少/样本偏题)则推翻、看真问题在哪。让数据决定痛点,而非预设。
- **设计痛点(5~8 个,沿旅程排)**:
  - **先读原声归纳标题,不先定标题再凑原声**(`voice-matching.md`)。
  - 分层 = 严重度 × 影响面(S0/S1/S2,见 `severity-rules.md`),优先前端可闭环的。
  - 每痛点用关键词在**全量**主题反馈里统计真实命中数(=pool),作量级佐证。原声**最多 30 条、酌情增加**,**宁缺毋滥**。
  - **「代表性」的定义(原声排序打分)**:`命中强度×3 + 带图+2 + 带订单号+1 + 有联系方式+1`,综合分高者优先采。**命中强度(本痛点词命中数−其他痛点词)是绝对主导项**——先保证"这条真讲这个痛点",再在同等代表性下优先选带图佐证、可定位(订单号)、可回访(联系方式)的。**绝不为凑图/凑电话而选跑题原声**,准确永远第一。
- 落成 `config.json`(结构见第 3 节)。
- **🔑 自下而上反向补漏(痛点初稿后必跑,治"主观枚举漏方向")**:`python3 scripts/enumerate_topics.py 子集.xlsx --report 报告.html --topic <同口径> --strict`。它让**数据自己吐出所有高频方向**,平铺成清单(命中数+样本+✦标记更像真方向的),再对照你已设计的痛点**逐条书面确认**:① 已覆盖→指出对应痛点 ② 没覆盖但真讲本主题→补痛点 ③ 属别类目/不成立→**写明排除理由**。**绝不默默跳过任何 ≥阈值方向——默默跳过正是遗漏根源**(实测:导航主题曾漏掉"举证无门"236条、"客服失联"136条两个最大方向,都因主观自上而下没想到)。脚本不自动判漏(判不准),判断权在你,但清单保证方向不缺。

## Step 4 — 核验一致性 🔑 (`verify.py`)
> 见 `rules/voice-matching.md`、`rules/credibility-rules.md`。机器把关,不靠人眼兜底。
- **机器校验(必跑)**:`python3 scripts/verify.py 报告.html [--config config.json]` 逐条核对每条原声是否真讲所在痛点,揪出 **✗错配**。**✗错配必须清零**。
- **标题⇄原声⇄数据三者一致**:抽 5 条原声问"是否都在讲标题这件事";pool 是全量真实命中数;主题命中过少却硬撑 → 收窄/并入/删除。**宁可 9 条全精准,不要 20 条混 7 条跑题**。
- **可信度**:原声按可追溯线索(截图/订单号/时间/证据词)分高/中/低,**只分层不验真**,保留"用户单方陈述、未核实"声明。
- 任意项不过 → 打回 Step 3。

## Step 5 — 提炼洞察 + 定优先级 + 出方案
> 见 `rules/impact-solution.md`。这是从"罗列痛点"跃迁到"给出结论"的关键一步。
- **① 提炼洞察(不止于罗列)**:把零散痛点收敛成**1~2 句核心矛盾 + 根因**。问自己:"这些痛点背后,用户最受不了的那件事是什么?根子在哪?"
  - 例:处罚申诉的核心矛盾 = "**骑手被罚却处处碰壁——入口藏、驳回黑箱、客服失联,救济链条全断**",根因是申诉链路设计偏向平台、不为骑手自证留路径。
- **② 定优先级(不只按 S 分层)**:用 **严重度 × 影响量(pool/占比) × 可改性(前端能否独立闭环)** 三轴判断**先打哪个**,给行动建议而非平铺。
  - 报告里痛点按 S0→S1→S2 排;但结论部分要明说"**先做 X(高严重+高频+易改),再做 Y**"。
- **③ 影响定量优先**:`impact.quant`(影响哪些指标,不编数值)优先,无则 `impact.exp` 体验影响。
- **④ 分析视角因地制宜**:`analysis` 按痛点性质选最贴的视角(触发场景/责任归属/高低频/新手老手…,见 `impact-solution.md`),**不死套某一种**。
- **⑤ 优化点落到页面(先看图,别猜)**:`fe` 单方案,结构化 `{page, now, to}`——【页面】现状→目标,研发可直接接。**带图主题务必先看截图定位真实页面**:跑 `python3 scripts/shots.py 数据.xlsx --source 类目 [--config config.json]` 归集用户截图 → `Read` 逐张看图 → 按 `rules/screenshot-grounding.md` 的「看图四问」得出真实页面名/元素/现状 → 填进 `fe.page/now/to`,并把作为依据的截图填 `fe.shot:{id,img}`(报告里渲染成方案旁缩略图,可追溯)。**page/now 必须从截图看到,不靠反馈文字猜**——这是"页面位置准、方案不简陋"的关键。⚠️ 分工:`shots.py` 只归集图(脚本不会看图),看图定位由你(模型)做。想更直观时,给 `fe.shot` 加 `marks` 在**典型问题截图**上标🔴红框圈出问题位置(只标问题、不做改后对比,见 `screenshot-grounding.md`),**批注不重绘、不伪造界面**。⚠️ **标注 box 坐标靠估必偏,写进 config 前必跑 `scripts/calibrate.py` 出校准图 Read 核对框对准了没**,对齐了再写(校准法见 `screenshot-grounding.md`)。
- **⑥ 突出价值(务必)**:每个痛点/行动都要回答"**做这件事有什么价值**"——解决多少用户诉求(pool/占比)、挽回什么指标、止住什么损失。填 `value` 字段,不填则按 pool 兜底。
- **⑦ 让人看懂(解读层)**:产出时填好 `summary`(核心发现,结论先行) / `readouts`(每图一句读图结论) / `logic`(拆解逻辑) / `nextstep`(下一步行动,带价值)。目标:**看报告的人能清晰get到"问题怎么拆的、为什么这么判、方案凭什么、看完该干嘛"**。

## Step 6 — 生成可视化 + 双校验 (`topic_report.py`)
> **唯一渲染引擎是 `topic_report.py`**。两种入口:
```bash
# ① 自动:引擎自己检索+挖词+采集+渲染(初稿,任意端)
python3 scripts/topic_report.py 数据.xlsx --sheet 表名 --topic 送达 --out 报告.html

# ② 精修:你构造好 DATA(含精准痛点/旅程/优化点/价值),调引擎的 render() 渲染
python3 -c "import sys;sys.path.insert(0,'scripts');import topic_report as tr; \
  import json; d=json.load(open('我的DATA.json')); open('报告.html','w').write(tr.render(d,'标题'))"
```
- DATA 结构见第 3 节配置契约(由 `topic_report.py` 的 `render()` 消费,是**唯一渲染源**;`report.py` 的取数层产出同构 DATA、转调同一 render())。
- 数据内联单文件 HTML。痛点卡**按 S0→S1→S2 排**,优化点落【页面】现状→目标。
- 生成后**必跑三校验(全绿才交付)**:① `verify.py`(原声⇄痛点,✗错配清零) ② `coverage_check.py`(该配没配/原声够/痛点够,默认严退出0) ③ `visual_check.py`(文字截断/布局/字号);**配了图再加** `shot_check.py`(配图合规)。再 `open` 打开过质检清单。这四道机器闸门覆盖"准不准/够不够/配的对不对/视觉",跑不过必须处理,不靠自觉。
- **自动产出大盘图**(按数据,缺则隐藏):① 占大盘占比(本主题 vs 其余;全量时隐藏) ② 分组分布(extMap 解析 `--group-field` 指定维度,骑手端'工作台'/C端'会员等级'等) ③ 问题分类占比(关键词互斥归一,与痛点 pool 多标签口径不同,各自标注)。

> 本 skill **聚焦"问题收集 + 问题分析"**:从原始反馈到旅程拆解、痛点挖掘、分层、原声佐证、洞察提炼、页面级优化点。**不含竞品对标截图、解决方案原型图等下游设计产出**。

# 3. 配置契约 (config.json) —— 你现场生成的领域知识

引擎 `render()`(及兼容入口 `report.py --config`)消费如下 DATA 结构。**换类目就整份重写**:

```json
{
  "focus_category": "处罚申诉",
  "col": { "cat": "来源", "content": "反馈内容" },
  "level_desc": { "S0": "……", "S1": "……", "S2": "……" },
  "scenes": ["跑单中触发违规", "罚单产生", "找申诉入口", "提交举证", "等待结果"],
  "max_voices": 20,
  "pains": [
    {"id":"P1","level":"S0","scene":"找申诉入口","title":"罚单不可申诉/找不到入口",
     "minlen":16,"maxlen":170,
     "kw":["不可申诉","无法申诉","申诉不了","找不到申诉","申诉入口"],
     "impact":{
       "quant":"受影响的数据指标(申诉成功率/客服工单量/留存…);有数据关联才填,优先展示",
       "exp":"体验层面影响(情绪/信任/挫败);必填,作兜底"
     },
     "analysis":{"lens":"分析视角名(按痛点性质选:触发场景/责任归属/高低频/新手老手…)","text":"一句话分析"},
     "idea":"一句话解决思路",
     "fe":[
       {"page":"涉及页面·位置","now":"现状(做法/缺陷)","to":"目标(改成什么)",
        "shot":{"id":"作为依据的反馈ID","img":"该截图URL",
                "marks":[{"box":[5,12,90,7],"kind":"problem","label":"问题描述"}]}},
       "或纯字符串方案(向后兼容)"
     ],
     "pages":["涉及页面1","涉及页面2"]}
  ],
  "journey": true
}
```
- **必填**:`focus_category`、`scenes`(场景/旅程顺序)、`pains`。`col`、`level_desc` 选填。`col` 一般**不用填**——引擎自动识别列名;只在识别错或想强制指定时覆盖(如 `{"content":"用户评价"}`)。
- 每个痛点的 `scene` 必须是 `scenes` 里的值;按 `scenes` 顺序映射,痛点详情区按 **S0→S1→S2** 优先级排序。
- **`impact` 定量优先**:`{quant, exp}` 对象。先判断有没有影响到可量化数据,有则填 `quant`(指出影响哪些指标,不编造数值),没有则只填 `exp` 体验影响。也兼容纯字符串(等同只有 exp)。见 `rules/impact-solution.md`。
- **`analysis` 分析视角(因地制宜)**:按痛点性质选最贴的视角,**不死套某一种**。两种写法:纯字符串(一句话),或结构化 `{"lens":"视角名","text":"分析"}`(lens 渲染为块标题)。见 `rules/impact-solution.md`。
- **`fe` 优化点(单方案,落到页面)**:数组,**优先结构化** `{page, now, to}` —— 渲染成「📄页面·位置　现状 → 目标」,研发/设计可直接接。也兼容纯字符串(向后兼容)。一个方案**兼顾新手好理解 + 老手高效**。
  - **`fe.shot`(截图佐证,素材足时每个方案都要配)**:`{id:"反馈ID", img:"截图URL"}`。看用户截图定位页面后,把作为依据的那张图挂上 → 报告里渲染成方案旁的缩略图(点开走灯箱),方案**可追溯到原图**。`page/now` 应从截图看到,不靠文字猜(见 `rules/screenshot-grounding.md`)。⚠️ **一个痛点有多个方案时,别只给第一个配图、后面裸奔**——只要该痛点带图原声充足,**每个结构化方案都应各自看图定位其页面、各挂一张 fe.shot**(coverage_check 闸门4 会拦"多方案只配部分图")。确实没有对应截图的方案才留空。无 shot 不影响渲染。
    - **`shot.marks`(选填,截图标注)**:`[{box:[x,y,w,h], kind:"problem", label:"…"}]`,`box` 为百分比(0~100)。加了 marks → 在**这张真实截图**上叠🔴红框圈出问题位置 + `label` 一句话说明(如"置灰的申诉入口不可点")。**只标问题、不做改后对比**——报告呈现的是"典型问题截图 + 红框圈出要改的地方",让人一眼看到问题在页面哪个位置。**批注不重绘、不伪造界面**:底图始终是真实截图,只叠红框标注层。无 marks → 仍是单缩略图(点开灯箱)。
- **`pages` 涉及页面**(选填):痛点整体涉及的页面;若 `fe` 已逐条带 `page`,可不重复填。
- **`journey`**(选填,顶层):设 `true` 且 `scenes` 是**真实用户旅程顺序**时,报告渲染旅程曲线图——曲线高低 = 各环节问题严重程度(内部按严重度×命中量算,但**展示用大白话**:节点标"N个痛点"、峰值标"最痛",不露加权数字),单色青线 + 红点标最痛,**无序号**。自动聚类初稿无真实旅程则不设,旅程图自动隐藏。
  - ⚠️ **journey=true 必须配 scenes**,否则旅程图静默消失(`render()` 的生成前自检会警告)。痛点的 `scene` 必须都在 `scenes` 里。
- `kw` 召回原声;`minlen/maxlen` 控长度(默认 16/170)。`max_voices` 每痛点最多采集条数(默认 30、酌情增加,典型/有代表性/带图优先,不必硬凑)。
- **`value`**(痛点级,选填):做这件事**有什么价值**(解决多少用户诉求/挽回什么指标/止住什么损失)。**分析中务必突出价值**;不填则引擎按 pool 自动兜底"预计缓解 N 条反馈对应的用户诉求"。

> **解读层(顶层字段,让看的人有理有据看懂;均选填,不填则引擎按数据自动兜底)**:
> - **`summary`**:开篇「核心发现」,1~2 句最重要结论的数组。结论先行,读者一进来就知道报告要讲什么。
> - **`readouts`**:每图「读图结论」,`{share/cats/wb/mix/journey}` 各一句"这个图说明了什么"。把图表从"摆数据"变"有观点"。
> - **`logic`**:痛点区「拆解逻辑」,一句话讲清"凭什么从数据拆出这些痛点"。让拆解过程可见 = 有理有据。
> - **`nextstep`**:结尾「下一步行动」数组,按优先级"先做/再做",**每条带价值**。不填则引擎按 S0→S1 + pool 自动生成带价值的行动建议。

> **自动产出的大盘图(引擎通用)**:除痛点外,报告还会按数据自动产出 ① **占大盘占比**(本主题 vs 其余,全量分析时隐藏) ② **分组分布**(从 extMap 解析分组维度;`--group-field` 可指定,**不指定则自动探测**常见维度——工作台/会员等级/用户类型/城市/渠道…,标题随实际维度动态显示,探测不到则隐藏) ③ **问题分类占比**(关键词互斥归一)。这三个图缺数据则对应区块自动隐藏,无需手动配置。

- [ ] 🔑 **跑 `scripts/coverage_check.py 报告.html [--config config.json]`,覆盖度达标(默认严,退出码0)**:四门充分性闸门——① **该配没配**(某痛点带图原声≥3却没配 `fe.shot` = ✗,必修;带图<3不配=合规不误伤)② **原声欠采**(pool≥20却只采不到20条 = ✗,补采)③ **痛点偏少**(<5个 = ✗,沿旅程多拆)④ **方案缺图**(某痛点素材足、有≥2个结构化方案却只配了部分图 = ✗,剩下的方案也各挂 fe.shot)。**这是"该配图/原声够/痛点够/方案图齐"的机器红线**,和 verify 一样跑不过必须处理,不靠自觉。真·宁缺毋滥场景(命中就少、图就少)天然全绿。

## 专业视角自检(生成时自检,三个角度拷问一遍)

precheck / verify / visual_check 只查 **形式 / 真实 / 视觉**,查不了"内容专不专业"。生成报告时,分别站三个专业视角把内容**拷问一遍**补这个缺口:

- 🔵 **业务视角**:S 分层是否按真实业务损失排(非按数量)?最伤业务/信任的排第一了吗?价值说到业务听得懂没(影响多少人 / 留存 / GMV)?
- 🟢 **产品视角**:痛点是"真问题"还是"现象"?根因找到没?几个痛点是不是其实是一个(有无重复 / 遗漏)?方案治本还是治标?
- 🟡 **设计视角**:优化点的交互 / 信息架构合理吗?有没有副作用(如"一键关弹窗"误伤重要通知)?分层用户都好用吗?

> **研发可行性不靠机器评**:改动范围、成本、技术坑交**真研发**判断,不假装可行性判断、制造虚假权威。

# 5. 页面设计规范(高级风)

- **配色**:中性灰底(#f6f7f9)+ 白卡片 + 一个克制品牌主色(京东红 #c8102e,可换)。S0/S1/S2 用红/橙/蓝。
- **层级**:Hero → 大盘 KPI → 诉求占比 → 趋势 → 痛点卡片(按场景顺序)。
- **痛点卡片**:左侧色条标层级;场景标签 + 场景描述/影响/思路/实际方案(分层视角)分区;底部"真实用户原声"可展开。
- **原声卡片**:① 反馈ID + 复制 + 截图数 → ② 正文 → ③ 元信息(城市/平台/版本/日期)→ ④ 截图缩略图(灯箱)。
- **交互**:条形图进场动画;原声默认 4 条,"展开全部"显示其余;灯箱支持 ←→ 键和 ESC。
- **健壮**:图片 `onerror` 兜底;`loading="lazy"`。
- **字号层级(递减分明)**:主标题(34~38) > 区块名(24~26) > 痛点标题(20~21) > 正文(13.5~14) > 注释/小标(11~12)。层级不可倒挂,相邻级差 ≥3px。
- **文字不截断**:长文字块(标题/痛点名/旅程标签/图例)统一加 `word-break:break-word; overflow-wrap:anywhere`;`body{overflow-x:hidden}` 兜底;SVG 内文字做边界保护(峰值/首尾 anchor 收拢、y 下限),避免被 viewBox 裁。
- **响应式**:KPI 等多列用 `auto-fit minmax(...)` 自适应换行;窄屏(≤480)缩字号、单列;饼图 svg+legend 在窄屏堆叠。
- **视觉核验(可视化后必跑)**:`visual_check.py` headless 多视口程序化探测——文字截断 / 排版布局 / 字号层级,不靠人眼。这些标准是机器硬规则,固化在脚本里。

# 6. 资产

- `scripts/profile.py` — 只读探查:结构、来源/分类占比、字段非空率。
- `scripts/mine.py` — jieba 自动挖高频词 + 二元共现(停用词读 `rules/stopwords.txt`),给痛点 kw 提供线索。
- `scripts/report.py` — 早期 config 驱动脚本,**渲染已归一到 `topic_report.render()`**(自带 HTML 模板已移除,薄壳转调唯一渲染源)。保留 `build_data` 取数层作参考与备用;新分析一律用 `topic_report.py`。
- `scripts/verify.py` — 🔑 **原声⇄痛点相关性校验器**:逐条核对每条原声是否真讲所在痛点,揪出错配。生成后必跑(Step4/质检)。
- `scripts/visual_check.py` — 🔑 **视觉核验器**(可视化后必跑):headless 多视口探测文字截断、排版布局、字号层级,程序化把关不靠人眼。
- `scripts/topic_report.py` — 🚀 **通用主题分析引擎(适配任何端)**:给一个主题(或不给)→ **自动识别列名**(任意结构,中英文)→ 自动检索、算大盘、聚类问题、采集原声 → 一键出报告初稿。**默认自动挖词,不预设任何端**;`--lexicon` 加载某端专属词典、`--group-field` 指定分组维度。支持单主题/多关键词/泛类/指定来源/全量。
- `scripts/shots.py` — 📱 **用户截图归集器(端无关,Step5)**:把某主题/类目的用户截图归集 + 下载 + 通用初筛(疑似截图/实景),出 `shots_index.json` 清单供**模型 Read 看图定位真实页面**。⚠️ 脚本只归集(不会看图),看图定位由模型做;结论填进 `fe.page/now/to/shot`。复用 topic_report 的列识别/取数,零业务硬编码。
- `scripts/calibrate.py` — 🎯 **标注坐标校准器(端无关,Step5)**:任意图+marks → 出带百分比网格的校准图,供**模型 Read 核对标注框有没有对准真实元素**。box 坐标靠估必偏,**写进 config 前必跑**;偏了调 box 重跑直到对齐。复用 shots.download/visual_check.find_chrome。
- `scripts/shot_check.py` — 🔎 **配图校核器(端无关,对称于 verify)**:机核每个 `fe.shot`——img/id 齐全、shot.id 可追溯到本痛点原声(揪盲挂)、marks 坐标合法(0~100 不越界)、无 fix/repl 旧格式残留。**不判"图是不是优化页面"**(需看图,那靠 `screenshot-grounding.md` 第0问)。`--strict` 有✗即退出码1,可挂 CI。**配了图就跑一遍**。
- `scripts/coverage_check.py` — 🧮 **覆盖度/充分性闸门(端无关,对称 verify/shot_check)**:管"够不够/该配没配"这一轴(verify管准不准、shot_check管配的图对不对)。四门:① **该配没配**——痛点带图原声≥3却没配 `fe.shot` = ✗(素材足才罚;带图<3不配=合规,不误伤宁缺毋滥) ② **原声欠采**——pool≥20却采不到20条 = ✗ ③ **痛点偏少**——<5个 = ✗ ④ **方案缺图**——痛点素材足、有≥2个结构化方案却只配部分图 = ✗(治"多方案只给第一个配图、后面裸奔")。**默认全严,任一硬项不过退出码1**(`--lenient-voices`/`--lenient-pains`/`--lenient-solshot` 可降级告警;阈值 `--min-imgs/--min-voices/--min-pains` 可调)。复用 `shot_check.extract_data/voice_ids_imgs`。**这是"配图/原声/痛点数/方案图齐 够不够"的机器红线,补上 SKILL 此前只靠文字提醒的缺口**。生成后必跑。
- `scripts/fetch_workbench.mjs` — 🤖 **用户之声工作台抓取内核(骑手 D 端,只读)**:node 脚本,自动读本机 **Chrome 的 jd.com 登录态**(`browser_cookie3`,免手动 curl/导出),走内网 `l-api-inner.jd.com`,按固定骑手 D 端 `category`+`channel=190` 全量分页抓近 **1/7/30 天**反馈,先 `count` 拿预期数再逐页拉到空页、按 `id` 去重、数量对不上写 `warnings`,产出 JSON(权限 0600)。用法 `node fetch_workbench.mjs --days 7 [--output-dir . --output-name x.json]`。**只读不改数据**;仅骑手 D 端口径,换端需改内置 category。
- `scripts/fetch_to_xlsx.py` — 🔗 **取数桥 + 一键入口(阶段0)**:把工作台反馈变成引擎可读 xlsx(sheet=`反馈一览表`)。两用:①`--days N`(N∈1/7/30)内部调 `fetch_workbench.mjs` 抓了直接转,一条命令到底;②`--json <文件>` 离线转已有 fetch JSON。列映射:`id/content/source→反馈ID/内容/来源`、`categoryPathNameList→一/二级分类`、`createdAt`(毫秒)→可读时间、`clientInfo.name→客户端`、`dmodel→机型`、`images→图片ID`、`extMap` **原样透传字符串**(供 `--group-field 工作台` 抠分组维度)、`contact/pin→联系方式/账号`。缺列(如城市,list 接口不返)自动降级隐藏。产出 0600。**这是"自动抓取"的落地入口,把 fetch 的 JSON 接上主引擎**。
- `scripts/export_xlsx.py` — 📊 **团队协作表导出器(端无关,交付可选)**:从报告 HTML 抽 DATA → 出 3-Sheet Excel。①痛点跟进表(左半查阅=你的结论只读 + 右半跟进=负责人/状态/排期/备注空列,状态下拉,S0红/S1橙/S2蓝行色) ②原声追溯明细(全量真实原声摊平,可筛选核查,**手机号默认脱敏** `138****8000`;`--contact full` 完整但慎发) ③配图证据(截图URL)。用法 `python3 export_xlsx.py 报告.html [--out 团队表.xlsx]`。**纯本地 openpyxl,不依赖任何在线服务**。HTML 是"给人看的报告",这份 Excel 是"给团队干活的数据底稿(筛选/认领/追溯)",**仅当下游需团队协作时才导**;只给人看则 HTML 已足够。
- `scripts/subset.py` — ✂️ **跨主题子集预处理器(端无关)**:有些主题不是数据现成的类目、靠内容词界定(如"路径规划""订单刷新""四环节易用性"),report.py 的 focus 匹配不到单一类目。用它 `python3 subset.py 原始.xlsx --topic "词1,词2,…" --name 主题名 --out 子集.xlsx`:①按词内容召回 ②「来源」列整列统一为主题名(供 report --focus 匹配)③新增「原来源」列(供来源分布/占大盘图仍有区分度)④打印原始全量数 → 传给 `report.py --total-all <全量>`,占大盘占比才准。**跨类目主题的标准第一步**,省去手写 pandas。
- **问题词典(可选外挂)**:默认不需要——引擎自动从高频词聚类(端无关)。想让某端分类更精准时,自建一份 JSON 传给 `--lexicon`,格式 `[["分类名",["关键词1","关键词2"]],…]`(例:`[["定位不准",["定位","导航","gps"]]]`)。不改脚本。
- `tests/smoke.py` — 🧪 **冒烟测试**(一键自测):跑通全部脚本+真实数据+列识别+双校验+截图标注/校准+配图校核+覆盖度闸门+子集预处理+团队表导出+**取数桥 fetch_to_xlsx(JSON→xlsx 列映射/时间戳转换/extMap 透传)**,断言不变量。**改任何脚本后跑一遍** `python3 tests/smoke.py`,确认没改崩。
- `requirements.txt` — 依赖声明(openpyxl/jieba/pandas;Pillow 可选,供 shots.py 截图初筛;**browser_cookie3 可选,供 fetch_workbench.mjs 自动读 Chrome 登录态抓取**)。换机器/移交先 `pip3 install -r requirements.txt`。自动抓取还需本机装 **node**。
- `rules/category-taxonomy.md` — 问题类目分类体系定义(Step2)。
- `rules/scene-ordering.md` — 使用旅程梳理法(Step2)。
- `rules/voice-matching.md` — 🔑 **标题⇄原声⇄数据一致性校验**(Step3/4,含真实翻车案例,最重要)。

- `rules/screenshot-grounding.md` — 📱 **看截图定位页面方法论(Step5)**:看图四问、截图→fe 映射、脚本归集/模型看图的分工。出方案前看图,页面位置才准。
- `rules/impact-solution.md` — 影响定量优先 + 分析视角因地制宜 + 优化点落页面(Step5)。

# 7. 执行风格

- 边做边用一句话同步进展(探查 / 梳理旅程 / 挖词 / 核验 / 出页面)。
- 用 TaskCreate 跟踪步骤。快速摸底先跑 Step A 引擎出初稿,重点主题再走人工精修。
- **换主题时整份重写 config.json**(旅程顺序 + 痛点),不沿用上一个主题的口径。
- 主题/核心类目不明确时主动问用户,不闷头猜。
- 交付前过质检清单,尤其 **verify.py ✗错配清零** 与 **文字无截断**。
- 交付时给结构化总结:数据结论(大盘+占比+工作台) + 痛点分层表(S0优先) + 页面级优化点 + 文件清单。
