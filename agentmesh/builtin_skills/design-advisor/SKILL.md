# /design-advisor · 新需求 → 设计洞察 → 有依据的建议

## 工作目录

执行本 skill 前，请先定位到仓库中的 `JD-ProductDetails-web/brain-frontend/` 目录，
所有路径均以此为根目录。

## 这个 Skill 做什么

设计师提交新需求，Skill 先理解需求本质，再结合知识库历史 Case 给出有洞察的设计建议：

1. **解读需求**：设计目的是什么、要解决什么用户/业务问题、成功标准
2. **概括设计建议**：核心方向和最重要的设计判断
3. **设计边界**：需要覆盖的状态、容易遗漏的边界、历史相关 Case 作为依据

历史 Case 是支撑建议的依据，不是建议的主体。

## 调用方式

```
/design-advisor <新需求输入>
/design-advisor <新需求输入> --confirm
```

**输入可以是：**
- 需求文字：`"预约商品需要展示国补到手价和腰带"`
- PRD 文件：`./prds/reservation-prd.md`
- Zero 链接：`https://relay.jd.com/file/design?id=xxx&node_id=6:571807`
- 截图：直接上传图片到对话，配合文字说明

**两阶段规则：**
- **默认（Phase 1）**：输出 outline，等待确认
- **加 `--confirm`（Phase 2）**：输出完整建议

> 不问设计师额外问题，所有判断自动推断，不确定时标注 ⚠️。

## 执行流程

### Step 1：解析输入

**文字 / PRD 文件**
- 读取内容，理解需求背景、业务目标、用户问题

**Zero URL**
- 若是短链接（非 relay.jd.com 域名），先用 `Bash(curl -sI <url> | grep -i location)` 自动解析，不询问用户
- 调用 `get_design_metadata` + `get_design_context` 获取设计稿内容
- 若 MCP 失败：降级为仅用文字，标注 `⚠️ 设计稿读取失败`

**截图**
- 分析 UI 元素、文案、组件结构，与文字输入合并

---

### Step 2：解读需求本质

在检索知识库之前，先独立思考这个需求：

- **用户问题**：这个需求要解决什么用户感知或行为问题？
- **业务目标**：背后的业务诉求是什么（转化、留存、合规等）？
- **设计挑战**：这个需求设计上最难的点在哪里？（信息层级、状态复杂度、用户认知负担等）
- **成功标准**：什么样的设计是好的？用户看到后会有什么反应？

这部分不依赖知识库，完全基于需求本身的分析。

---

### Step 3：检索知识库

**第一步：检索已录入的 Case**

读取 `public/design-kb/knowledge/INDEX.md` 和 `public/design-kb/knowledge/component-naming.md`，用关键词匹配：

| 相关级别 | 判断规则 |
|---|---|
| 🔴 强相关 | 关键词与 Case 的组件名/核心场景完全匹配，**或** ui_pattern 完全一致 |
| 🟡 中等相关 | 关键词部分匹配，**或** ui_pattern 部分一致（如同为 popup-sheet 但业务场景不同） |
| 🟢 背景参考 | 同属一个功能区，但关键词和 ui_pattern 均不重叠 |

**ui_pattern 匹配说明：**
用 grep 提取每个 Case frontmatter 中的 `ui_pattern` 字段：
```bash
grep "ui_pattern:" public/design-kb/knowledge/scene/strategies/nationalSubsidy/xxx-reasoning.md
```
将本次需求的 UI 结构（从输入描述或设计稿推断）与 Case 的 `ui_pattern` 对比。
即使关键词完全不同（如「家电组合购买」vs「商超省心搭配」），若 ui_pattern 相同（如都是 `card-grid, pdp-main`），仍判定为强相关。

对强相关和中等相关的 Case，读取：
- `## 核心设计决策`
- `## 状态覆盖表`
- `## 可复用的设计模式`
- `## 有意排除的内容`
- frontmatter 的 `screenshots` 字段

**第二步：检索素材登记表（INDEX 无匹配时执行）**

若 INDEX.md 中强相关 Case 数量为 0，读取 `public/design-kb/knowledge/registry.md`，用同样的关键词匹配「待录入」状态的记录。

匹配到登记记录时，在 Outline 末尾展示选项，让设计师决定下一步：

```
---

## 📎 发现相关历史素材（尚未录入知识库）

| 需求名称 | 关联点 | 素材链接 |
|---|---|---|
| [需求名称] | [与本次需求的关联点，一句话] | [查看设计稿](relay链接) · [查看PRD](prd链接) |

**请选择下一步：**

A. **直接查看建议**（基于已录入案例 + 通用判断，不等待）
   → 回复「A」或「--confirm」

B. **等待录入后再看**（AI 现在录入以上素材，完成后给出包含历史依据的完整建议）
   → 回复「B」，录入需要 2-5 分钟
```

**选择 A 时：**
按正常流程输出完整建议，未录入素材以「📎 参考素材」形式附在「四、历史依据」末尾：

```markdown
### 📎 参考素材（未录入，仅供参考）

以下需求可能与本次相关，尚未完整录入知识库，无法作为正式历史依据引用：

- **[需求名称]**：[查看设计稿](relay链接) · [查看PRD](prd链接)
  关联点：[一句话]
```

**选择 B 时：**
逐条调用 `/design-reasoning-input` 完成录入，每条完成后输出进度：
```
✅ 已录入：[需求名称]（1/2）
⏳ 正在录入：[需求名称]（2/2）
```
全部完成后自动继续输出完整建议，此时历史依据章节包含刚录入的案例。
同时将 registry.md 中对应记录状态更新为「已完成」。

**知识库预检：**
- INDEX.md 不存在：报错退出，提示先运行 `/knowledge-update`
- INDEX 和 registry 均无匹配：继续执行，建议标注 `⚠️ 无历史依据，为通用判断`

### Step 4：生成 Outline（Phase 1）

Outline 按以下顺序输出，**历史 Case 放在最后作为依据，不放在最前**：

```markdown
# 设计建议 Outline — [需求名称]

---

## 一、需求解读

**要解决的问题：** [1-2句，用户视角]

**业务目标：** [1句，业务视角]

**设计挑战：** [最难的点是什么，1-2句]

**成功标准：** [什么样的设计是对的，1句]

---

## 二、初步设计判断

[3-5条核心判断，每条1-2句。这是 AI 对这个需求最重要的设计洞察，
不是罗列信息，而是给出有观点的判断。
例："腰带是唯一承载期限信息的入口，不宜在此处直接展开文字，
应沿用点击弹窗模式——这在 multisku Case 中已验证。"]

---

## 三、动笔前需要确认的问题

1. [问题] → 不确认的后果：[后果]
2. ...

（上限 5 条，只列真正会导致返工的问题）

---

- [其他需要覆盖的状态]
- ⚠️ [不确定是否需要覆盖的状态]

---

## 五、相关历史 Case（作为依据）

| 相关级别 | Case | 与本需求的关联点 |

---

```

### Step 6：下载到本地（用户回复「下载」时执行）

用户回复「下载」后，把完整建议同时写出 MD + HTML 两个文件到本机的 **Downloads 目录**，方便用户直接打开或转发：

**文件路径：**
- `~/Downloads/[需求名称缩写]-[YYYY-MM-DD].md`
- `~/Downloads/[同名].html`

> 不再写入仓库内的 `advisor-output/` 目录——本 skill 是"只读知识库 + 给建议"，不再产出归档物。
> 用户的输出物落在他自己的 Downloads，便于后续整理 / 删除 / 分享，不污染仓库。

写入前确认目录存在（macOS / Linux 默认存在）：
```bash
mkdir -p "$HOME/Downloads"
```

MD 文件内容即完整的 Phase 2 输出，在开头加一行元信息：

```markdown
> 生成时间：[YYYY-MM-DD HH:MM]
> 需求输入：[用户原始输入的前50字]
> 知识库引用：[Case 文件名列表]

---

[完整的设计建议内容]
```

**HTML 文件生成规则：**

HTML 结构按以下章节顺序渲染，每个章节用不同的可视化方式：

| 章节 | 可视化方式 |
|---|---|
| 一、需求解读 | 4格信息卡片（问题/目标/挑战/成功标准） |
| 二、推荐参考设计稿 | 参考稿卡片 + 可复用/需修改标签列表 |
| 三、设计任务清单 | checkbox 行，复用/修改/新增/排除用不同颜色标签 |
| 四、需要覆盖的状态 | 带风险标签的表格，⭐行黄色高亮 |
| 五、历史依据 | 相关性标签 + Pattern 摘要折叠卡片 |
| 六、知识库更新提醒 | 提示条 |

**HTML 样式规范：**
- 配色体系：国补绿 `#0AAD48`，服务金 `#b5691a`，紫色 `#7F77DD`，背景 `#F5F4F0`
- 字体：`-apple-system, "PingFang SC", sans-serif`
- 风格：卡片式，圆角，轻阴影，无多余装饰
- 内嵌全部 CSS，不依赖外部资源，双击即可在浏览器打开

输出：
```
✅ 已下载到本地 Downloads 目录：

📄 ~/Downloads/[文件名].md
🎨 ~/Downloads/[文件名].html  ← 双击在浏览器打开，图文可视化版本

可以直接在 Finder（macOS）/ 文件管理器中找到，或拖给同事 / 上传到云盘。
```

**约束：**
- 只在用户明确回复「下载」时才写文件，不自动写
- 文件名中的需求名称取前 10 个中文字符，去掉特殊符号
- MD 和 HTML 同名，同时生成
- 文件写到 `~/Downloads/`，**不写入仓库目录**，不需要 `.gitignore`

## 关键约束

### 内容约束
1. **需求解读优先。** 必须以需求解读开头，不能直接跳到历史 Case。
2. **建议要有观点。** 「设计建议」章节给出判断，要有立场，不是信息罗列。
3. **历史 Case 是依据，不是主体。** Case 放在最后作为支撑。
4. **引用必须有出处。** 每条来自历史 Case 的建议标注 `Case 名 §章节`。
5. **区分历史依据和通用判断。** 无 Case 支撑的建议标注 `⚠️ 通用判断，无历史依据`。
6. **不跳过 Phase 1。** 必须先输出 outline，确认后才输出完整建议。
7. **不主动写入文件。** 只在用户明确回复「下载」后才写入 `~/Downloads/`，不修改知识库任何文件，不在仓库内产出归档物。

### 输出格式约束（防止重复和混乱）
8. **每个 Case 只出现一次。** 「四、历史依据」章节中，每个 Case 最多出现一个 `###` 区块，绝对不允许同一个 Case 重复出现。生成前先列出要写的 Case 列表，确认无重复后再逐一输出。
9. **每条「需特别注意的历史决策」只引用一次。** 同一段引用（`▎ ... — 来源：...`）不在同一个 Case 区块内重复出现。
10. **「本次需求中」段落每个 Case 只写一次。** 不允许同一段落内容重复多次。
11. **数量上限严格执行。** 强相关 Case ≤ 2 个；Blocker ≤ 5 条；设计建议 3-5 条；状态枚举 ≤ 10 条。
12. **输出前自检。** 生成完整建议后，在写入输出之前，检查是否有重复的 Case 区块、重复的引用段落、重复的「本次需求中」段落，有则删除重复项再输出。
