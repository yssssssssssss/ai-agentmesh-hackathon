# Relay Component Set Architect

把用户已经画好的多个状态样式封装成稳定、可复用、可实例化的 Relay 组件集。目标是识别这些状态之间的共同结构与差异：结构性差异收敛为少量变体，开关差异做布尔属性，固定槽位内的同族切换做子组件集变体，可替换外部资产才做实例替换或插槽，可变文案做文本属性。

核心原则：**设计稿是视觉权威；用户已经画好的状态是输入，不是让 agent 凭空生成。封装动作只做归纳、克隆、转组件、加属性、整理变体和必要注册。不要重画，不要用变体枚举所有内容差异。**

本 skill 的定位是：**已有多状态样式 -> 反向封装组件集**。

它不是：**单个基础组件 -> 自动生成缺失状态**。如果用户只提供一个基础组件，并希望生成选中、未选中、展开、收起、禁用、加载等缺失状态，应交给另一个 skill：`relay-component-variant-generator`。

## 工程铁律

- **像素保真优先。** 默认流程是 `clone -> createComponentFromNode(clone)`，在克隆体上原地转组件；不要手工重画。只有当运行时确认 `createComponentFromNode` 会导致坐标、Auto Layout、实例裁切等异常时，才允许手工重组，并且必须截图自检。
- **最终外露优先单一主组件。** 组件封装的默认目标不是生成一排可替换实例，而是生成一个主组件/单一卡片，让使用者在这个组件里切换所有合理样式。只有确认是不同组件族、不同布局骨架或不同业务入口时，才拆成多个主组件。
- **固定槽位用子组件集 VARIANT，不用 INSTANCE_SWAP。** 如果某个位置固定引用同一个子组件集，例如左上角 icon、右下角指标、底部 tag、利益标题行，这个位置的切换语义应是子组件集的 `VARIANT` 轴，并在主组件上暴露或透传这个变体控制；不要把同一子组件集的各个变体当成一组 `INSTANCE_SWAP` 候选。
- **属性必须绑定。** 只 `addComponentProperty` 不会生效；必须把返回的 property key 绑定到子节点：`TEXT -> componentPropertyReferences.characters`，`BOOLEAN -> componentPropertyReferences.visible`，`INSTANCE_SWAP -> componentPropertyReferences.mainComponent`。
- **property key 不可硬编码。** `addComponentProperty` 返回的 key 带随机 `#uid`，每次都可能不同。脚本必须保存返回值；实例 `setProperties` 也必须使用运行时 key。
- **实例属性 key 不从空实例猜。** `inst.componentProperties` 在 `setProperties` 前可能为空；需要从主组件或组件集的 `componentPropertyDefinitions` 读取，再按基础名匹配。
- **BOOLEAN 只作为设计开关，不作为渲染唯一依赖。** 删除或重组绑定节点时，Relay 可能清理相关 BOOLEAN 属性。若接入渲染器，关键显隐应能通过稳定 node name 直接设置 `visible` 兜底。
- **透明 wrapper 必须透明。** 用于包裹 tag、badge、icon 等局部内容的 frame/component 默认 `fills=[]`，避免白底遮盖父组件。
- **布局自检必须做。** 封装后至少截图主组件、子组件集和 2-3 个实例组合。若出现裁切、错位、文字重叠、黑屏、实例透明，先检查 `layoutMode`、子节点 `x/y`、wrapper `fills`、实例 `opacity/visible`、以及是否把画布绝对坐标带入组件内部。

## Relay 平台限制（实测踩坑，必读）

以下都是在实际封装中验证过的 Relay 行为，违反会导致"脚本返回 ok 但实际没生效"这类静默失败。

- **非 VARIANT 属性必须加在组件集（COMPONENT_SET）层，不能加在变体组件上。** 在变体 `COMPONENT` 上 `addComponentProperty('TEXT'/'BOOLEAN'/'INSTANCE_SWAP')` 不会冒泡到组件集，实例 `componentProperties` 里看不到它，`setProperties` 会静默忽略该 key（返回 ok，文案/显隐毫无变化）。正确做法：在 `componentSet.addComponentProperty(...)` 上加，再把返回 key 绑到各变体内部对应子节点的 `componentPropertyReferences`。**一个集级属性可以跨多个变体绑定**（如 `主文案` 同时绑 4 个变体的主文本节点），代价是共享同一个默认值；若要每个变体独立默认值，就各起唯一属性名。VARIANT 轴例外——它本就生在集上、由变体子件名派生。
- **TEXT 节点 `autoRename` 默认为 `true`，直接改图层名会被自动还原（名字跟随 `characters`）。** 给文本图层起语义名（如把绑定到 `主文案` 的节点改名为 `主文案`）前，必须先 `node.autoRename = false` 再设 `node.name`，否则回读会发现名字变回了文案内容甚至旧草稿值。Frame/Instance 无此问题。
- **改 VARIANT 轴名要用 `componentSet.editComponentProperty(旧轴名, { name: 新名 })`，不能只改变体子件名。** 仅把子件名从 `属性1=A` 改成 `新名=A` 不会更新组件集的属性定义轴名，造成"子件名 vs 定义轴名"不一致的脏态。`editComponentProperty` 会联动把所有变体子件一起重命名，保持一致。改前先确认 0 实例引用或可接受联动。
- **改 TEXT / BOOLEAN / INSTANCE_SWAP 属性名也用 `component.editComponentProperty(旧key, { name: 新名 })`，别走"删旧加新"。** 实测本次「`收藏数#BSXipD` → `种草数#BSXipD`」`editComponentProperty` 一行搞定，`#uid` **完整保留**，节点 `componentPropertyReferences.characters` 自动跟随，所有现有实例的 `setProperties({['收藏数#BSXipD']: ...})` 不会失效（key 变了，但 Relay 会同步实例覆盖到新 key 上）。反例：用 `addComponentProperty(新名, ...)` + 重新绑定子节点 + `removeComponentProperty(旧key)`，旧实例上的覆盖会变孤儿、`#uid` 也换了一个，下游脚本里硬编码的 `'收藏数#BSXipD'` 全断。
- **重命名 VARIANT 的「值」（option，非轴名）没有干净 API；改子件名会 desync 选项列表。** 把变体子件名从 `展示信息=回放V2` 改成 `展示信息=直播回放`，子件名是更新了，但 `componentSet.componentPropertyDefinitions['展示信息'].variantOptions` 仍缓存旧值 `回放V2`（多次 `getNodeByIdAsync` 重读依旧）——这是 derived-read 不随子件重命名 prune。`editComponentProperty(轴, { variantOptions: [...] })` 返回 ok 但**静默无效**（VARIANT 选项是只读派生值，不接受重写）。后果：实际渲染/变体解析按子件名走没问题、下游无引用就不炸，但属性面板下拉会留一个指向新设计的旧名 ghost 选项。想彻底干净只能 recombine 变体或重开文件让其重算。若该值有实例引用，**先评估**再改。
- **`editComponentProperty(轴, { defaultValue: '某值' })` 对 VARIANT 轴有效，是修「非法默认组合」的正解。** 多轴变体集的默认态 = 各轴 `defaultValue` 的笛卡尔组合；若该组合无对应变体（如 `标签属性=直播` × `展示信息=Live`，而 Live 只存在于 `内容` 下），默认态就是坏的。逐轴 `editComponentProperty(轴, { defaultValue })` 改到一个**真实存在**的组合（如 `内容`+`图文`）即可，实测生效、可回读 `componentPropertyDefinitions[轴].defaultValue` 验证。
- **增删变体后，组件集会被 Relay 重新套上自动布局（HORIZONTAL/VERTICAL）。** 组件集本不该是自动布局（变体应是自由网格）。用户每次新增/删除变体，都可能让 `layoutMode` 变回非 `NONE`、把变体挤成一行/一列。收尾时要重新 `set.layoutMode = 'NONE'`，再手动把变体摆成规整网格并 `resizeWithoutConstraints` 贴合。
- **实例 `componentProperties` 枚举可能返回空对象，即使属性已生效。** 不要依赖它来取 key 或判断属性是否存在。改从 `componentSet/主组件.componentPropertyDefinitions` 取 key（VARIANT 轴 key 是纯名字，TEXT/BOOLEAN/SWAP 带 `#uid`），直接 `inst.setProperties({ [key]: value })` 即可（BOOLEAN/TEXT/VARIANT 实测均有效）。
- **嵌套实例（子组件）的属性默认不冒泡到外层组件实例面板。** 外层组件里固定引用的子组件实例，其变体/文本/显隐属性默认不可在外层实例上编辑；需要把该嵌套实例 `isExposedInstance = true`，它的属性才会暴露到外层实例，供使用者切换变体或改文案。
- **改 TEXT 组件属性用 `setProperties` 不需要预加载字体，且别乱预加载。** `inst.setProperties({ [textKey]: '新文案' })` 只改属性覆盖值、复用节点既有字体，无需 `loadFontAsync`。反而若机械地遍历预加载子树字体，碰到不可用字体（如 `JDZhengHei V2.0 Bold`）会抛错，因脚本原子性导致**整段回滚**、实例都没建成。只有直接写 `node.characters` 才需要先 `loadFontAsync`（此时按节点自身 `fontName` 逐个 try/catch 加载，跳过加载失败的）。验证文案可编辑时，直接 `setProperties` + 截图即可。
- **变体切换是否“回弹尺寸”取决于上下文。** 纯净实例（无尺寸覆盖）在自由布局里切变体会自动回弹到新变体的尺寸；但在自动布局父级里，实例的 `layoutSizingVertical/Horizontal = 'FIXED'` 会把尺寸锁死，切变体不回弹（`setProperties` 返回 ok，但卡片高度/比例纹丝不动）。被手工 `resize` 过的实例也会带尺寸覆盖、同样锁死。
- **可变尺寸的变体要驱动外层布局，必须打通整条 hug 链。** 想做到“切封面比例/尺寸 → 整卡高度跟随”：① 变体组件本身要是自动布局 hug（`NONE` 布局的变体没内容可 hug，实例设 `HUG` 会被回弹成 `FIXED`）；② 引用它的实例设 `layoutSizingVertical = 'HUG'`；③ 外层帧也 hug（`primaryAxisSizingMode='AUTO'`）；④ 帧上的 overlay（角标、标签条）设 `layoutPositioning='ABSOLUTE'` + 约束钉位（如话题条 `vertical:'MAX'` 钉底、角标 `MIN/MIN` 钉左上），不参与流式排列。任一环是 FIXED/NONE 都会断链。
- **改了组件结构后，下游引用它的旧实例可能残留孤立覆盖，导致渲染空白（数据却完全正常）。** 典型：删/重建组件里的子实例后，下游实例仍挂着指向被删节点的覆盖，截图整片空白，但逐层 dump `fills`/尺寸/`visible` 全对。`resetOverrides` 在 Relay 不一定存在；最干净的修法是**删掉下游旧实例、重新 `createInstance` 一个**（全新实例无覆盖、自动镜像正常组件），再补回 `isExposedInstance`/sizing。
- **截图在并发编辑或刚改完结构后可能滞后，但数据层（fills/尺寸/visible/属性）是真相。** 反复空白/异常先逐层 dump 数据核对，别只信截图；必要时新建一个干净实例强制重渲再截。

## 改造既有组件：先查引用、按影响面决定改哪层（实测）

收敛/重构一个已经在用的组件前，先评估影响面，别直接动共享件。

- **动结构前先全页面扫实例引用。** 遍历 `relay.root.children` 每页 `await setCurrentPageAsync` + `findAll`，统计 `mainComponent` 属于目标集/变体的 INSTANCE 数量与分布。共享基础件（可能上百处引用、躺在“公共组件”页）**绝不能改变体结构**——会联动炸掉所有实例；只能在本地副本或外层做，纯图层名/命名清理则安全（不破坏结构与渲染）。
- **收敛冗余外层变体轴 = 释放变体成独立组件。** 当外层组件集只是重复枚举内层子组件的状态（外层 `互动状态` ≈ 内层 `名称`）、且外层引用很少时：把要保留的那个变体 COMPONENT 用 `parent.insertChild(idx, variant)` reparent 出组件集 → 它变成独立组件，原来指向它的实例**自动改指向、无需重绑**；再对内层实例 `isExposedInstance = true` 让使用者直接选状态；最后删掉旧集其余无用变体（删前复查 0 引用）。
- **单组件（非集）的“状态展示”用多实例，不要重新加变体。** 收敛成单组件后，spec 页要展示“各种状态”就铺多个实例、每个切内层变体到一个状态（避免重新引入变体爆炸）。注意：内层计数等若是实例文本覆盖，会被各实例继承同一个值，要逐个实例改 `node.characters` 才能各不相同。

## 适用场景与不适用场景

适用场景：

- 用户已经画完多个状态，想封装成组件集。
- 用户希望把多个 frame / group / instance 整理成组件母版。
- 用户希望判断哪些差异适合做 `VARIANT`、`BOOLEAN`、`INSTANCE_SWAP`、`slot`、`TEXT` 属性。
- 用户提供多个 Relay 节点，希望反向封装成组件集。
- 用户选中多个相似状态样式，希望自动归纳成可维护组件。

不适用场景：

- 用户只提供一个基础组件，并希望生成缺失状态；转交 `relay-component-variant-generator`。
- 用户想重新设计组件视觉。
- 用户想生成一个全新组件。
- 用户只想修改文案或替换图标。
- 用户想做页面级多状态，而不是单个组件族封装。
- 多个节点明显不是同一个组件族。

## 0. 先解析来源 skill 的约束

原 `relay-componentize` skill 的有效部分：

- 从 Relay 链接解析 `fileKey` / `nodeId`，`17-1747` 形式要转成 `17:1747`。
- 先用 metadata / screenshot / design script 读节点树，再决定哪些做属性。
- 优先在克隆体上保留原视觉，避免手工重建。
- `TEXT`、`BOOLEAN`、`INSTANCE_SWAP`、`VARIANT` 要按角色规划，属性 key 不能硬编码。
- 属性必须绑定到子节点，单纯 add property 不会生效。
- 组件清单、ID、属性不要写死进 md；权威源在 Relay 文件和运行时扫描。
- 若接入渲染器，只在新增区块类型或拼装范式时改 schema / assembly / render。

原 skill 的项目私有链接在当前环境可能不存在，例如 `design/assembly-spec.md`、`design/content-schema.md`、`render/render-scheme.js`。使用本 skill 时不要依赖这些路径固定存在；先在当前仓库查找对应文件，再决定是否接入。

## 1. 前置检查

1. 解析用户给出的 Relay URL，得到 `fileKey` 与一个或多个 `nodeId`。如果只给了父容器，先读取其子节点，判断每个子节点是否代表一个状态样式。
2. 对每个候选状态调用 `get_design_metadata(nodeId)` 和 `get_screenshot(nodeId)`，先理解结构和视觉；不要只看第一个状态。
3. 写任何 Relay 脚本前，读取 zero-design/design-on-zero 资源：
   - 先列资源，找到 `design-on-zero/SKILL.md` 或同义的 design script skill。
   - 读取 `design-on-zero/references/relay-plugin-api.index.md`。
   - 需要精确 API 时，再读取或搜索 `relay-plugin-api.d.ts` 中的具体符号。
4. 用一次只读或临时可回滚探测确认运行时能力：`createComponentFromNode`、`combineAsVariants`、`addComponentProperty`、`componentPropertyReferences`、`setProperties`、`swapComponent`。探测节点必须删除，不留下临时组件。
5. **扫同 Relay 文件已有组件命名样本，归纳命名规约。** 在任何 `createComponentFromNode` / `combineAsVariants` 之前，必须先跑一次跨页扫描，统计每页 COMPONENT / COMPONENT_SET 的命名形态——是否带场域前缀（`图文/...`、`商卡/...`、`内容下挂卡片/商品卡/...`）、嵌套层级用什么分隔（`/` 还是 `-`）、变体子件名格式（`轴=值,轴=值` 还是 `属性1=...`）、当前页 page name 是否本身就是场域名（`[p]图文详情页` → 场域 `图文`）。把归纳结果作为「目标命名」记下，新组件、新子组件集、嵌套实例图层名必须沿用同款规约，不要拍脑袋起一个跟整文件不搭的名字。参考扫描脚本骨架：
   ```js
   for (const page of relay.root.children) {
     await relay.setCurrentPageAsync(page)
     const comps = page.findAll(n => n.type === 'COMPONENT' || n.type === 'COMPONENT_SET')
     // 收集 page.name + comp.name 的样本，至少 5–10 条
   }
   ```
   反例：在 `图文/详情页`、`商卡/搜索横卡`、`内容下挂卡片/商品卡/标题` 共存的文件里，新建 `底部互动区` 或 `底部互动区/Icon/收藏`（缺场域前缀、混中英）就是典型的命名漂移。
6. 若当前项目有组件/渲染约定，优先读取现有 `assembly-spec`、`content-schema`、`render-scheme` 或同名文件；组件名、属性名、子组件集名优先沿用现有 token 和命名体系，没有再按本 skill 的通用规则执行。

注意 API 漂移：有的环境支持 `createComponentFromNode`、`addComponentProperty`、`setProperties` 等运行时能力，但当前 API index 未必列出。用之前必须通过 d.ts、已有脚本或一次小型探测脚本确认；不能凭记忆硬写。

## 2. 组件族判断

封装前必须判断多个节点是否属于同一个组件族。不能确认同族时，必须停止并输出风险原因，不继续封装。

可以归并为同一个组件族的情况：

- 根节点尺寸相近。
- 布局结构相似。
- 主内容区域一致。
- 交互语义一致。
- 差异集中在状态、显隐、内容替换或局部扩展。
- 节点命名或视觉结构存在明显关联。

不应该归并的情况：

- 根结构完全不同。
- 主内容语义不同。
- 布局模式完全不同。
- 尺寸差异过大且不是 `Size` 属性能解释。
- 多个节点属于不同业务组件。
- 差异需要重写大量结构才能统一。

判断方法：

1. 先比较根节点尺寸、布局方式、主内容区域和视觉层级。
2. 再比较子节点语义：标题、图标、媒体、操作区、标签、提示、展开区是否有对应关系。
3. 最后比较差异是否能被 `VARIANT`、`BOOLEAN`、`INSTANCE_SWAP`、`slot`、`TEXT` 表达。
4. 如果需要大量移动、重画或重构才能统一结构，判定为不同组件族。

## 3. 状态样式拆解

先判断目标属于哪类组件或状态组。视频场域可以优先参考下表；非视频组件也按同样方法处理：先找共同骨架，再找状态差异。

| 类型 | 常见节点 | 优先组件名 |
|---|---|---|
| 视频卡片 | 封面、标题、作者、时长、播放量、角标、进度 | `视频卡片/基础`、`视频卡片/横版`、`视频卡片/竖版` |
| 播放器控制层 | 播放/暂停、进度条、倍速、清晰度、全屏、弹幕 | `播放器/控制层`、`播放器/进度条` |
| 沉浸式短视频 | 作者区、标题文案、互动列、商品/活动挂件 | `短视频/沉浸信息层`、`短视频/互动列` |
| 直播间 | 主播信息、在线人数、关注、礼物、商品袋、连麦状态 | `直播/信息层`、`直播/互动操作区` |
| 评论/输入 | 评论入口、输入框、表情、发送、热评 | `评论/输入条`、`评论/热评卡` |
| 商业化挂载 | 广告标、商品卡、优惠券、品牌露出、转化按钮 | `商业化/视频挂件`、`商业化/商品条` |
| 安全与权限 | 年龄、敏感内容、会员、付费、地理限制、下架 | `视频状态/权限提示`、`视频状态/安全标识` |

对每个状态节点建立对照表：

| 对照项 | 记录内容 |
|---|---|
| 根节点 | name、size、layout、position |
| 共同结构 | 每个状态都存在的文本、图标、容器、背景、控制层 |
| 状态差异 | 颜色、显隐、尺寸、图标替换、内容区展开、遮罩、边框、文案 |
| 缺失节点 | 某些状态没有的层，判断是否应补成隐藏层或拆成插槽 |
| 可复用子结构 | 适合拆为嵌套组件的标签、按钮、互动项、信息行 |

## 5. 组件属性决策规则

组件集的变体只表达**结构性或互斥状态差异**，内容差异用属性解决。

推荐变体轴：

| 变体轴 | 值示例 | 什么时候使用 |
|---|---|---|
| `场景` | `信息流` / `详情页` / `沉浸` / `直播` | 布局骨架明显不同 |
| `画幅` | `16:9` / `9:16` / `1:1` / `3:4` | 媒体容器比例影响排版 |
| `密度` | `紧凑` / `常规` / `完整` | 文案行数、互动信息多少不同 |
| `播放状态` | `默认` / `播放中` / `暂停` / `加载` / `结束` / `错误` | 控制层和状态遮罩不同 |
| `权限状态` | `可看` / `会员` / `付费` / `受限` | 锁层、CTA 和提示文案结构不同 |
| `直播状态` | `未开播` / `直播中` / `回放` | 仅直播组件使用 |

避免这些变体轴：

- 文案内容、播放量、昵称、时间、价格：用 `TEXT`。
- 标签是否展示、是否关注、是否点赞、是否有商品：优先用 `BOOLEAN`。
- 图标、头像、封面、按钮图形：先判断是否属于同一插槽的多个互斥状态；若是，先封装为子组件集，主组件固定引用该子组件集，并把子组件集的 `VARIANT` 轴作为主组件可切换控制；只有单一外部替换资产或跨组件族入口才直接用 `INSTANCE_SWAP` 或图片填充槽位。
- 颜色主题：优先用样式/token 或少量子组件，不要把颜色枚举成大组件集。

### 同一插槽优先子组件集

当多个差异节点出现在**同一个位置 / 同一语义插槽 / 互斥切换**时，必须先向上抽象为一个子组件集，而不是把每个样式散成并列母版。

适合先封装为子组件集的情况：

- 同一左上角 icon 插槽里有 `种草` / `视频` / `直播` / `榜单` 等互斥状态。
- 同一右下角操作插槽里有 `收藏` / `浏览` / `点赞` / `评论` 等互斥状态。
- 同一 tag 插槽里有 `排行榜` / `促销` / `商品特质` / `描述` 等互斥状态。
- 同一状态标识位里有 `会员` / `付费` / `限免` / `已结束` 等互斥状态。
- 同一按钮插槽里有主按钮 / 次按钮 / 危险按钮等同语义状态。

正确结构：

```text
主组件/卡片
  - 左上角Icon：固定引用 子组件集「卡片/Icon/左上角」，主组件暴露「左上角Icon类型」VARIANT
  - 右下角操作：固定引用 子组件集「卡片/指标/右下角」，主组件暴露「右下角指标类型」VARIANT
  - 底部Tag：固定引用 子组件集「卡片/底部Tag」，主组件暴露「底部Tag类型」VARIANT
```

错误结构：

```text
主组件/卡片
  - 左上角Icon=种草  单独母版
  - 左上角Icon=视频  单独母版
  - 左上角Icon=榜单  单独母版
```

判断口诀：**同一位置、同一语义、互斥切换，先子组件集，再暴露子组件集 `VARIANT`；跨语义、业务可插拔、结构不固定，再考虑 `INSTANCE_SWAP` 或 `slot`。**

### 什么时候用 Variant

当差异代表组件整体状态，并且影响多个视觉属性或结构表现时，使用 `VARIANT`。

适合：

- 默认 / 选中 / 未选中
- 默认 / 禁用
- 默认 / 加载中 / 成功 / 错误
- 未完成 / 已完成 / 已过期
- 展开 / 收起
- 主类型 / 次类型 / 危险类型
- 小 / 中 / 大
- 横向 / 纵向
- 强提醒 / 弱提醒
- 空态 / 正常态 / 异常态

不适合：

- 只是换文案。
- 只是换图标。
- 只是显示 / 隐藏一个小标签。
- 只是换图片。
- 只是业务内容不同。
- 用 `BOOLEAN`、固定子组件集 `VARIANT` 或真正外部 `INSTANCE_SWAP` 更轻量就能解决。

### 什么时候用 Boolean

当差异只是某个元素显示或隐藏，且不会改变组件整体状态时，使用 `BOOLEAN`。

适合：

- 显示图标 / 隐藏图标
- 显示徽标 / 隐藏徽标
- 显示标签 / 隐藏标签
- 显示副标题 / 隐藏副标题
- 显示关闭按钮 / 隐藏关闭按钮
- 显示分割线 / 隐藏分割线
- 显示辅助说明 / 隐藏辅助说明
- 显示底部操作区 / 隐藏底部操作区

注意：如果显隐差异同时代表组件整体状态，例如“展开 / 收起”，优先作为 `VARIANT`；如果只是可选附加元素，才做 `BOOLEAN`。

### 什么时候用 Instance Swap

当某个区域需要替换成**不同组件族**、外部业务方传入的单一组件、头像、封面、商品图、复杂入口时，才使用 `INSTANCE_SWAP`。

先做这个判断：替换候选是否属于同一插槽的多个互斥状态？

- 是：先把这些候选封装成一个子组件集；主组件固定引用这个子组件集，并暴露/透传子组件集的 `VARIANT` 轴。不要把它建模成 `INSTANCE_SWAP`。
- 否：如果是外部业务方传入的单一组件、图片、资产，或确实是跨组件族的可插拔入口，再直接使用 `INSTANCE_SWAP`。

如果当前 Relay API 无法把嵌套子组件集的变体轴透传到主组件属性面板，仍然要在架构判断中标记它是“固定子组件集 VARIANT”。可以先保留主组件内的默认变体实例，并在汇报中说明 API 限制和下一步，不要为了能切换而退化成一组语义错误的 `INSTANCE_SWAP`。

适合：

- 外部传入的 icon 组件，而不是当前组件族内固定的一组 icon 变体
- 外部传入的操作组件，而不是当前组件族内固定的一组操作变体
- 外部传入的状态标识组件，而不是当前组件族内固定的一组状态变体
- 头像可替换
- 商品图可替换
- 奖品卡可替换
- 跨组件族按钮实例可替换
- 外部 tag 组件可替换，而不是固定 tag 子组件集的变体
- 外部 badge 组件可替换，而不是固定 badge 子组件集的变体

不适合：

- 同一位置的多个 icon 各自散成独立母版，然后直接挂给主组件。
- 同一位置的多个 tag 各自散成独立母版，然后直接挂给主组件。
- 可以被一个变体轴表达的互斥状态却用多个松散 swap 候选表达。
- 主组件某个固定位置永远引用同一个子组件集，只是需要切换这个子组件集的变体。

如果替换后布局完全不同，不能用 `INSTANCE_SWAP`，应考虑 `slot` 或拆组件。

### 什么时候用 Slot

当某个区域需要承载外部传入的复杂内容，并且内容类型不固定时，使用 `slot`。

适合：

- 卡片底部操作区
- 弹窗内容区
- 列表 item 右侧操作区
- 模块头部右侧区域
- 任务卡片扩展内容区
- 底 bar 上方复合组件区
- 通知条右侧操作区
- 商品卡片营销扩展区

判断标准：

- 如果这个区域未来会放入不同结构的模块，而不是只换一个图标或文案，就用 `slot`。
- 如果这个区域是业务方自定义内容入口，就用 `slot`。
- 如果这里的内容复杂度超过一个简单 `INSTANCE_SWAP`，就用 `slot`。

### 什么时候用 Text Property

当差异只是文案内容变化时，使用 `TEXT` 属性。

适合：

- 标题
- 副标题
- 描述
- 按钮文案
- 数字
- 价格
- 状态文案
- 提示文案

如果文案变化伴随状态变化，不应只做 `TEXT` 属性；状态仍应被建模为 `VARIANT`，状态内的文案可继续暴露为 `TEXT`。

## 6. 命名约定

### 6.1 组件 / 组件集命名

**总原则：沿用同 Relay 文件的已有命名规约。** 第 1 节扫描结果就是真相源——目标文件用什么格式，新组件就用什么格式。不要套别的项目里的命名习惯，也不要拍脑袋。

通用 fallback（同文件无明显规约时才用）：

- **路径式 `场域/组件名[/子件名]`**，分隔符 `/`。场域取自页面 page name（如 `[p]图文详情页` → `图文`、`[p]↘️ 商卡✅` → `商卡`），或文件里高频出现的业务前缀。JD V16 典型实例：`图文/详情页`、`商卡/搜索横卡`、`内容下挂卡片/商品卡/标题`。
- **子组件集名要继续带场域前缀**，不要从主组件名「截短」起头。错例：主组件 `图文/底部互动区`，子集起名 `底部互动区/Icon/收藏` ← 缺场域 + 混中英；正例：`图文/底部互动区/收藏图标`。
- **嵌套实例（在主组件里固定引用的子组件集 instance）的图层名也要语义化**，跟「图标」「头像」「标签」这种业务角色对齐；不要保留 `Icon` / `Avatar` / `Tag` 这种英文占位名。`isExposedInstance=true` 后，这个图层名就是使用者在实例面板上看到的属性 label。
- **组件内部所有 frame / group 也要语义化，不留 `Frame 2085665547` / `容器 20121214724` / `编组 3备份 10` / `Rectangle 11113938` / `image 2502` 这种 Figma 自动 / Sketch 历史名。** `clone -> createComponentFromNode` 会原样带入设计稿历史层名，绝大多数是 Figma 自动 ID 或者从 Sketch / Adobe XD 导入残留（中文「容器 + 大数字」「编组 + 数字 备份 + 数字」最常见，来自老 Sketch 工作流）。封装收尾必须扫一遍组件树，把每一层按业务角色重命名（`互动条 / 评论入口 / 互动数据区 / 收藏组 / 评论组 / 点赞组 / 编辑图标 / 指示条 / HomeIndicator`）；TEXT 节点要先 `autoRename = false` 再改名。**矢量内部**（`Group` / `Clip path group` / `Union` / `Vector` 这类深嵌套矢量基元）可以不动，没人翻那一层。判断口诀：使用者在 Relay 图层面板上点开组件可能看到的层，都要起业务名；只在矢量绘制深处出现的不必。扫描判定建议：层名匹配正则 `/^(Frame |Rectangle |Group$|Ellipse |Vector |image |图层|容器 \d{6,}|编组 \d+|Clip path group)/` 都视为待重命名。
- **变体子件名（COMPONENT_SET 里的多个 COMPONENT）则用 `轴名=值[,轴名=值]`** 格式，例如 `状态=默认` / `状态=已种草` / `标签属性=直播,展示信息=信号柱`，沿用同文件样本。
- **变体子件名 = `轴名=值`**，多轴用 `,` 分隔，写法与同文件保持一致（`,` 后有无空格、是否用 `=` 都对齐；如同文件是 `标签属性=直播,展示信息=信号柱`，你也用 `,` 不加空格）。轴名优先用业务概念（`状态` / `场景` / `画幅` / `密度` / `样式`），不要用 Relay 默认的 `属性1`。
- **示例脚本骨架（封装收尾内部层批量改名）：**
  ```js
  // 转 Component 之前，先把母版 clone 内部的所有 frame/group 按业务角色改名
  const masterClone = await relay.getNodeByIdAsync('<cloneId>')
  const bar = masterClone.children[0];      bar.name = '互动条'
  const entry = bar.children[0];            entry.name = '评论入口'
  const editIcon = entry.children[0];       editIcon.name = '编辑图标'
  const dataRow = bar.children[1];          dataRow.name = '互动数据区'
  dataRow.children[0].name = '种草组'       // wrap 1
  dataRow.children[1].name = '评论组'       // wrap 2
  dataRow.children[2].name = '点赞组'       // wrap 3
  // TEXT 节点要先关 autoRename 再改
  const tCount = await relay.getNodeByIdAsync('<textId>')
  tCount.autoRename = false; tCount.name = '种草数'
  // 然后再 createComponentFromNode(masterClone) 转成组件
  ```
- **同混语言风险**：路径里出现 `图文/底部互动区/Icon/收藏` 这种中文夹一段英文（`Icon`），属于命名漂移，必须改成全中文 `图文/底部互动区/收藏图标` 或全英文，看同文件主流走向。

### 6.2 属性命名

属性名按业务角色命名，不按图层外观命名。

| 内容 | 属性类型 | 命名示例 |
|---|---|---|
| 标题/描述 | `TEXT` | `视频标题`、`视频描述`、`评论文案` |
| 作者/主播 | `TEXT` | `作者昵称`、`主播昵称`、`认证文案` |
| 数据 | `TEXT` | `播放量`、`点赞数`、`评论数`、`在线人数` |
| 时间 | `TEXT` | `视频时长`、`发布时间`、`剩余试看` |
| CTA | `TEXT` | `主按钮文案`、`转化按钮文案` |
| 显隐 | `BOOLEAN` | `显示作者区`、`显示关注按钮`、`显示商品挂件`、`显示广告标` |
| 同位互斥图标/tag/操作 | 子组件集 `VARIANT`，主组件暴露/透传该变体轴 | `左上角Icon类型`、`右下角指标类型`、`底部Tag类型` |
| 单一外部资产 | `INSTANCE_SWAP` 或图片槽 | `封面图`、`头像`、`外部商品卡` |
| 结构状态 | `VARIANT` | `播放状态`、`画幅`、`密度`、`权限状态` |

文本默认值要像真实视频内容，不要用 `Title` / `Lorem`。例如：`夏日海边旅行 Vlog`、`@创作者昵称`、`12.8万次播放`。

## 7. 母版选择规则

- 选择结构最完整、信息最完整、扩展性最好的状态作为母版参考。
- 如果存在展开态，通常优先参考展开态作为结构母版。
- 如果存在有图标、有标签、有按钮的状态，通常优先参考信息最完整的状态作为母版。
- 如果某状态只代表极端或异常状态，不应作为母版。
- 最终母版必须基于 clone 创建，不能直接修改用户原始设计稿。

母版不是“默认态”的同义词。默认态常适合做组件集默认展示，但结构母版应选择最能覆盖未来扩展的状态。

在执行任何画布操作前，必须输出封装计划：

```text

  - 主组件：
  - 子组件集：
  - 嵌套实例图层名：
  - 变体子件名格式：

建议组件集名称：
候选节点数量：
建议母版节点：
```

## 9. 封装流程

1. dump 每个状态节点的结构：列出所有 `TEXT`、疑似图片/封面、图标、按钮、标签、控制层、遮罩层、数据区和挂件层。
2. 对齐各状态的节点树：按语义 name、位置、尺寸、文本角色和视觉层级匹配同源节点，识别共同结构与差异节点。
3. 标记每个差异：
   - `fixed`：纯视觉骨架，不暴露属性。
   - `text-prop`：实例需要改的文案。
   - `visibility-prop`：业务上可有可无的层。
   - `nested-component-set`：同一插槽、同一语义、互斥切换的多个候选，例如左上角 icon、右下角指标、底部 tag。必须先归并为子组件集。
   - `child-variant-prop`：主组件某个固定位置引用一个子组件集，并需要切换这个子组件集的变体轴。
   - `swap-prop`：只用于替换单一外部组件/头像/封面槽位，或真实跨组件族可插拔入口。
   - `slot`：可插入不同子内容的区域，例如商品挂件、底部操作区、展开内容区。
   - `variant-axis`：结构状态，才进入组件集。
4. 先为同位插槽制定子组件集计划：子组件集名称、变体轴、变体值、默认变体、主组件固定引用方式、主组件上暴露/透传的属性名。不能把同位候选停留为多个并列母版，也不能把同一子组件集的变体误建成 `INSTANCE_SWAP`。
5. 为主组件集制定架构计划：最终外露是否为单一主组件、主组件变体轴、属性清单、插槽、嵌套组件集、子组件集变体透传策略、每个状态对应的变体名。
6. 克隆原状态节点，不修改用户原设计稿。
7. 若运行时确认支持组件集/变体能力，严格按顺序执行：先封装子组件集，再封装主组件，再绑定属性，再创建实例预览，再截图自检；否则先创建一组命名一致的组件，保留后续合并组件集的路径。
8. 封装子组件集时，所有同位候选必须进入同一个 `COMPONENT_SET`，变体轴通常命名为 `类型` / `状态` / `尺寸`。不要把它们停留为画布上散落的多个独立母版。
9. 封装主组件时，优先 `clone -> createComponentFromNode(clone)`。如果该方式导致内部坐标或 Auto Layout 异常，才改用 `createComponent()` 重组；重组时必须复制原节点尺寸、圆角、填充、裁切、布局，并把子节点坐标归一到组件本地坐标。
10. 主组件中固定引用子组件集的实例或默认变体，不直接引用一堆散落的同位独立组件。主组件属性名应指向插槽角色和变体轴，例如 `左上角Icon类型`、`右下角指标类型`、`底部Tag类型`。
11. 固定子组件集的切换优先暴露/透传子组件集 `VARIANT`。只有当该槽位未来会替换为不同组件族、外部组件或不固定结构时，才把这个槽位建成 `INSTANCE_SWAP`。
12. 添加组件属性后必须立即绑定到稳定可定位的子节点。绑定前先给节点改成语义化 name，例如 `Title / 标题`、`Icon / 左侧图标`、`Content Slot / 内容插槽`；视频场景可用 `Video Title / 视频标题`、`Cover / 封面图`、`Duration Badge / 视频时长`。**同时把组件内部所有 frame / group 也按业务角色批量改名，不留 `Frame 2085665547` 这种 Figma 自动 ID**（见 6.1 节示例脚本）；矢量基元深处可不动。
13. 绑定关系必须符合属性类型：`TEXT` 绑定 `characters`，`BOOLEAN` 绑定 `visible`，`INSTANCE_SWAP` 绑定实例节点的 `mainComponent`。固定子组件集切换不绑定到 `mainComponent`，而是绑定/透传该子组件集的变体属性。保存运行时返回的完整 property key，不硬编码 `#uid`。
14. 文本属性需要固定容器策略：标题、昵称、播放量、按钮文案等长内容必须设置合适的固定宽高、截断、最大行数或 `textAutoResize`，不能让实例内容撑乱卡片。
15. wrapper/透明容器的 `fills=[]`，尤其是 tag、badge、icon、slot 占位。否则默认白底可能遮住主卡背景或封面。
16. 每个变体必须保留一致的属性名和子节点语义；某个状态没有的节点，优先保留为隐藏层或插槽占位，除非结构确实应拆成独立组件。
17. 创建至少 2-3 个实例预览，用 `setProperties` 覆盖不同组合。实例属性 key 从主组件 `componentPropertyDefinitions` 或脚本中保存的 property key 获取，不从空实例猜。
18. 封装后必须截图主组件、每个子组件集、每个实例预览。若出现裁切、错位、文字重叠、黑屏或透明，先修复再汇报。

示例脚本骨架：

```js
const src = await relay.getNodeByIdAsync('<nodeId>')
if (!src) throw new Error('Source node not found')

const clone = src.clone()
clone.name = '__draft 母版__'   // 临时草稿名；转 Component 后按 6.1 节命名规约改正式名（如 '场域/组件名'）
relay.currentPage.appendChild(clone)

// Prefer runtime-supported createComponentFromNode if confirmed.
// Otherwise create a component and move cloned children into it while preserving bounds.
return {
  sourceId: src.id,
  cloneId: clone.id,
  cloneName: clone.name,
  width: clone.width,
  height: clone.height,
}
```

> 变体子件名（一个 COMPONENT_SET 里的多个 COMPONENT）则用 `轴名=值[,轴名=值]` 格式，例如 `状态=默认` / `状态=已激活` 或 `标签属性=直播,展示信息=信号柱`，沿用同文件样本。

## 10. 场景补充：视频 UI 特殊处理

- 封面图固定为媒体槽位，维持裁切比例。不要让标题、标签、浮层改变封面容器尺寸。
- 播放按钮、暂停按钮、加载 spinner、错误重试层属于 `播放状态`，不要用多个 `BOOLEAN` 拼出互斥状态。
- 时长、清晰度、会员、广告、直播中等角标通常是子组件：角标文案用 `TEXT`，角标显隐用 `BOOLEAN`。
- 标题在信息流卡片通常 `maxLines=1` 或 `2`；沉浸式文案通常 `2-3` 行并需要展开态。长文案必须验证截断策略。
- 互动列中的点赞、评论、收藏、分享如果处在同一操作插槽，先封装为一个操作子组件集；数字用 `TEXT`，主组件固定引用该子组件集，并暴露/透传它的操作类型 `VARIANT`。
- 直播在线人数、热度、榜单、礼物动效入口变化频繁，优先拆成嵌套实例，避免主组件变体爆炸。
- 商业化内容和安全/权限提示要独立成可插拔层，不能和基础播放层强耦合。
- 弹幕、字幕、进度条等有时间轴含义的元素，设计组件只表达静态状态；不要尝试在 Relay 组件里模拟真实播放逻辑。

## 11. 变体收敛规则

创建组件集前，先问自己：

- 这个差异是否改变布局骨架？是，才考虑 `VARIANT`。
- 这个差异是否只是内容、数量、显隐、图标替换？不是主组件结构变体；若是同位互斥替换，先做子组件集，再把子组件集 `VARIANT` 作为主组件内的可切换控制。
- 两个变体是否能共用同一套属性名？不能共用时，优先拆成两个组件。
- 变体总数是否超过 `场景 x 画幅 x 密度 x 状态` 的必要组合？超过就拆层。

推荐上限：一个组件集尽量不超过 12 个变体。播放器/直播等复杂场景，拆为多个组件集而不是做一个巨型组件集。

## 12. 停止条件

遇到以下情况必须停止，不继续执行：

- 无法读取节点。
- 用户选择的节点少于 2 个。
- 用户选择的节点不是同一个组件族。
- 多个状态之间结构差异过大，无法归并为同一组件。
- 无法判断哪个状态适合作为母版。
- 变体数量超过 12 个。
- design script API 不支持必要的组件属性操作。
- 运行时无法确认属性绑定能力，或 `addComponentProperty` 后无法绑定到子节点。
- 执行后出现严重尺寸异常、文本重叠或内容溢出。
- 截图自检发现主组件、子组件集或实例预览明显不可用，且无法在当前轮修复。

停止时输出：

```text
当前不适合直接封装为组件集。

原因：
建议处理方式：
原始设计稿是否被修改：否
```

## 13. 注册或接入渲染器

只有当用户明确要“接入渲染 / 写 schema / 让代码可实例化”，或当前项目已有渲染流水线时才做。

执行顺序：

1. 用 `rg --files` 找到类似 `render-scheme.js`、`content-schema.md`、`assembly-spec.md` 的项目文件。
2. 读取现有命名 token、block schema、属性填充工具，沿用项目风格。
3. 新增 block 时，字段用组件业务语义；视频组件可参考：
   - `title`、`description`、`authorName`、`avatar`、`cover`
   - `duration`、`playCount`、`likeCount`、`commentCount`
   - `isLive`、`isAd`、`isPaid`、`hasProduct`、`permissionState`
4. 如果只是已有视频 block 的同类变体，且组件名和属性遵循约定，通常不改 schema。
5. 不把组件 ID、随机 property key 写进 md。渲染器应按组件名 token 和属性基础名解析；组件清单、组件 ID 和带 `#uid` 的属性 key 以 Relay 文件运行时扫描为权威。
6. 对关键显隐逻辑，渲染器应能通过稳定 node name 直接设置 `visible` 兜底，不把 BOOLEAN 属性作为唯一依赖。

## 15. 汇报格式

封装完成后简洁汇报：

- 新组件或组件集：名称 + node ID。
- 最终外露形态：单一主组件/单一卡片，或说明为何必须拆为多个主组件。
- 变体轴：例如 `场景`、`画幅`、`密度`、`播放状态`。
- 属性清单：基础名 + 类型 + 绑定对象；不要把随机 `#uid` 当作长期文档字段。
- 子组件集：名称 + node ID + 变体值 + 主组件暴露/透传的变体轴。
- 固定槽位说明：哪些槽位固定引用子组件集并通过 `VARIANT` 切换；哪些槽位是真正 `INSTANCE_SWAP`，以及为什么。
- 实例预览：node ID + 覆盖的组合。
- 特殊处理：如标题截断、封面比例、状态层拆分、商业化挂件拆分。
- 截图：调用 `get_screenshot` 给用户检查。

如果因为当前 API 不支持组件属性绑定或组件集创建，只完成了结构分析/克隆组件，也要明确说明缺失的 API 和下一步可行路径。
