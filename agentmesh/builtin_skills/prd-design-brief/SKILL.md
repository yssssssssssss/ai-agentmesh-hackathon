# PRD → 设计简报 + 结构化模块清单

读 PRD，产出两样东西并**停在确认门**：
1. **人看的设计简报** —— 背景/价值/目标、场域页面组件定位、迭代/创意分类、交互UI提炼、待确认项。
2. **下游契约** —— 结构化模块清单（含场域/页面/组件路由字段），供下游出稿 skill 直接消费。

**本 skill 只做分析与定位，不出设计稿、不自动调用任何下游 skill。**

## 触发

- 粘贴 `joyspace.jd.com/pages/...` 链接
- `读PRD` / `分析PRD` / `设计todo` / `需求分析` / `这个需求是创意还是迭代`
- 直接粘贴 PRD 正文文本 / 原型截图

## 三条铁律（违反即返工）

1. **可追溯**：Phase 1–4 每条结论必须挂 **PRD 出处（行号或原文引用）**。**推断 vs 原文严格分标** —— 凡不是原文直接写的，标 `[推断]`；某层 PRD 没写标 `[PRD未述]`。
   - > 反面教材：曾把 PRD 中"送达卡片点击\<送达指引\>触发重算"（一个触发点）写成"送达卡片**新增**送达指引入口"，"新增"是推断却没标注 → 越界失真。
2. **场域识别扫真实仓库**：不假设固定层级。启动时实扫 `local-life/` 目录树建索引，匹配不上就诚实标"仓库暂无，需新增"，**绝不硬套**同名组件。
3. **停在确认门**：Phase 5 输出后停下，等用户确认再由用户决定调哪个下游出稿 skill。

## 场域根

```
local-life 根：jd-design-system-md-v16/product-architecture/local-life
频道（第1层）：不写死清单——每次用 find 实扫（见 Phase 2 第1步）。
  原因：频道目录会改名（曾从 wuliu/pindao 改为 Logistics 物流/Channel 频道…），
        写死清单必过时；实扫永远对齐现实，这也是铁律2。
层级形态不统一：有的 频道/page/页面/components/*.md，有的 频道/组件/ 直接铺，有的带 foundations/tokens。
→ 必须每次实扫，不背固定路径、不背固定频道名。
```

## Phase 0 · 取内容 + 预检门

**取内容优先级**：
1. **Joyspace 链接** → 用 `joyme_joyspace` MCP（HiOffice 免浏览器登录，走用户 ERP 权限）。
   - 先 `get_page_basic_info` 拿标题/权限，再 `get_normal_json_content` 拿 Slate JSON。
   - ⚠️ **不要用 zero-design 的 `check_knowledge_source`** —— 它是另一套后端权限，同一篇文档会报"无文档读取权限"。joyme_joyspace 能读。
2. **粘贴文本** → 直接用。
3. **原型截图** → 读图，视觉信息优先级最高（PRD 纯文本常漏 UI 细节）。

**切片降噪**（关键）：PRD 常含大段与交互无关内容 —— 后台/算法/大模型 prompt/埋点/SQL/数据清洗。**先切出交互/UI/页面相关段落，滤掉噪音再分析**。
- 噪音信号词：`你是...专家/分析师`（prompt）、`label_id`/`AND`（SQL）、`埋点`/`MQ`/`t+1`（后台）、`大模型`/`算法输出`（算法侧）。

**门**：取不到正文 / 全是非交互内容 → **停**，如实告知原因，不硬编。

### 标准 PRD 章节 → Phase 定位表（双通道取数）

京东本地生活标准 PRD 为 8 段骨架。**PRD 若遵循此结构，按章节精准取数**；**不遵循则回退上面的降噪 grep**（真实 PRD 常不规范，两通道并用）。

| 标准章节 | 内容 | 落到 | 处理 |
|---|---|---|---|
| 一、版本控制 | 成员/排期/评审记录 | Phase 0 元信息 | 看「设计」成员是否在场→是否到设计阶段；评审记录→成熟度。**不进分析正文** |
| 二、项目概述 | 产品现状/数据现状/预计解决问题/目的/目标/方案概述 | **Phase 1** | 直接对齐背景·问题·价值·目标 |
| 三、方案流程图 | 需求范围（用户身份 + 客户端 APP/小程序/H5）、流程图 | 需求范围→**Phase 2**；流程图→**Phase 4 交互层** | 取「端 + 用户身份」维度 |
| 四、功能列表 | 序号/功能/备注/**重要度** | **Phase 3** | 功能=模块原料；重要度=优先级列 |
| 五、交互文档 | UI地址/交互说明（页面/设计稿/详细说明） | **Phase 4 改动矩阵** | 提炼展示/交互/状态三层 |
| 六、数据需求 | 埋点/客诉/使用情况 | — | **剔除**（设计不关心） |
| 七、非功能需求 | 上线城市/AB/降级/数据过渡 | — | **剔除**（与 UI/交互无关） |
| 八、数据回顾 | 上线后 review | — | **剔除**（复盘，非设计输入） |

> 记忆口诀：**二三四五 = 设计核心**，**一 = 元信息**，**六七八 = 噪音剔除**。

## Phase 1 · 背景 / 价值 / 目标 / 用户场景（带出处）

结构化五项，每条挂行号，推断项标 `[推断]`：

| 项 | 说明 |
|---|---|
| 背景 | 项目大盘、为什么做 |
| 问题 | 量化现状痛点（数据尽量引原文） |
| 价值 | 预期收益（引原文数字） |
| 目标 | 本期要做什么（一句话范围） |
| **用户场景** | 用户（骑手/C端…）处于哪个使用场景：浏览中 / 下单前 / 支付前 / **购买后·配送中** / 流失召回。**只定场景**（背景层面"在什么情境下用"），具体点哪跳哪的操作动线留 Phase 2.5 |

## Phase 2 · 场域 / 页面 / 组件识别

按序执行（**这是核心差异能力**）：

1. **扫仓库建索引**：
   ```bash
   # 频道层
   find <local-life根> -maxdepth 1 -type d
   # 命中频道下的页面 + 组件 md
   find <local-life根>/<频道> -name "*.md" | sort
   ```
2. **定场域**：PRD 属哪个频道？给判据（关键词/页面名/业务线）。
3. **定端 + 用户身份**（来自标准 PRD 三·需求范围）：PRD 涉及哪个客户端（**APP / 小程序 / H5·Web**）、哪类**用户身份**（骑手 / C端用户 / 商家…）。设计规格按端分，**此维度不可漏**；PRD 未明确则标 `[PRD未述]`。
4. **匹配页面**：PRD 提到的页面 ↔ 仓库已有页面目录。命中=存量；未命中=候选新增页。
5. **匹配组件**：PRD 的 UI 元素 ↔ 页面下 `components/*.md` 或组件目录。
   - ⚠️ **同名不同场景要辨别**：如"送达卡片"在抢单大厅 `订单卡片.md` 有，但那是抢单大厅场景；PRD 若指订详页的送达卡片，是不同场景，**不可直接复用**，标"同名不同场景，需新增语境"。
6. **诚实报告缺口**：PRD 主战场页面若仓库无文档，**必须显式指出** —— 这是影响下游能否出稿的最大前提。

## Phase 2.5 · 用户操作动线

Phase 1 已定**宏观阶段**（什么场景）。这里画**微观操作动线**——用户在已识别的页面/模块间**点哪、跳哪、一步步怎么走**（依赖 Phase 2 的页面/模块结果，故放这里）。

- **主动线**：用箭头串关键节点（含触发条件），标 PRD 出处；断点/分支/旁路也画出来。
- **格式**：`起点(触发) → 步骤1 →(条件)步骤2 → … → 终点(完成什么)`。
- **旁路**：不在主动线上的独立入口（如 IM 场景）单独标出，别硬塞进主链。
- PRD 未述的环节标 `[PRD未述]`，不脑补。

## Phase 3 · 模块清单（结构化 · 可路由下游）

PRD 拆成模块，每模块一行：

| 模块 | 场域/频道 | 端 | 命中页面 | 命中组件md | 迭代/新增 | 新增子类 | 重要度 | 置信 | PRD出处 |
|---|---|---|---|---|---|---|---|---|---|

- **迭代/新增 判定**：按 [分类判据.md](分类判据.md) 裁——主判据"落点页命中仓库=迭代(存量迭代/局部优化)/未命中=新增(0-1页)"；**新增必再判 `创意页/非创意页`**(决定下游走哪条出稿 skill)；边界情况查该文件判例表，**保证结论可复现**。
- **新增子类**：仅"新增"填 `创意页`(需原创视觉→创意出稿) / `非创意页`(现有组件拼装→非创意出稿)；迭代项留 `—`。
- **端**：APP / 小程序 / H5·Web（来自 Phase 2 第 3 步）。
- **重要度**：PRD 自己标的优先级（四·功能列表的重要度列，如 P0/P1/高中低）；PRD 未标则 `[PRD未述]`。
- **置信**：高/中/低——**我判分类的把握**（描述越略越低）。⚠️ 重要度 ≠ 置信：前者是 PRD 的优先级，后者是我判断的确定性，两者独立。
- 附 **整体倾向**（N迭代 / M新增〔含创意页/非创意页各几〕）+ **下游路由建议**（详见 [分类判据.md](分类判据.md) 五）：
  - 新增·创意页 → 走**创意出稿 skill**；新增·非创意页 → 走**非创意出稿 skill**；
  - 迭代项 → 走存量组件改稿 skill；
  - **若迭代所依赖的存量页在仓库无文档 → 标明"须先补存量文档才能改稿"**，否则下游无锚点。

## Phase 4 · 模块改动矩阵（与 Phase 3 咬合）

承接 Phase 3 的每个模块，逐行展开成矩阵——**页面 × 模块 × 改动类型 × 三层**，与模块清单**一一对应（同名同序、行数一致）**：

| 页面 | 模块 | 改动/新设计 | 展示层 | 交互层 | 状态层 | 出处 |
|---|---|---|---|---|---|---|

- **改动/新设计**：迭代=`改动`（在存量页/组件上加或改什么）；创意=`新设计`（0-1 新建什么）。
- **展示层**：展示什么字段 / 视觉元素 / 文案（含数据来源）。
- **交互层**：触发时机、用户操作、跳转 / 回跳。
- **状态层**：状态枚举（默认 / 展开 / 空 / 异常…）+ 分支逻辑（条件 → 展示差异）。
- 每格挂 PRD 出处；某层 PRD 没写就留空并标 `[PRD未述]`，**不臆造**（待确认项自然浮现在空格里）。

## Phase 5 · 产出 + 确认门 🛑

按 [OUTPUT-TEMPLATE.md](OUTPUT-TEMPLATE.md) 产出：
- **① 人看的设计简报**（Phase 1–4 汇总 + 待确认项）。
- **② 下游契约**（Phase 3 清单 + Phase 4 三层矩阵转 front-matter/json）。
- **③ 分析简报 HTML**（可选，用户要"出个 HTML"时）：把 ① 渲染成可分享的**只读报告**页，套 [report-template.html](report-template.html)。

> ⚠️ **③ 的红线**：HTML 只是**分析结果的可视化**（背景价值目标卡片 + 模块清单表 + 改动矩阵 + 待确认项），**绝不含任何 UI 页面还原 / 线框图 / mockup**——UI 出稿是**下游 skill 的活**，本 skill 出 UI 就违反铁律3、且与下游重复。报告页顶部必须标注"本页为需求分析，非设计稿"。

**待确认项** = Phase 4 矩阵里所有 `[PRD未述]` 的格子 + Phase 2 报告的存量文档缺口，汇总成一段。

输出后 **停**。提示用户：确认后由用户决定调用哪个下游出稿 skill。**本 skill 不自动往下走。**

## 已确认的设计决策（来自需求方）

- PRD 输入形态：**Joyspace 在线文档链接**为主。
- 分类粒度：**按页面/模块逐个判 + 整体倾向聚合**。
- 分析后：**停在确认门，不自动调下游出稿 skill**。
- 场域范围：**local-life 为主战场**。
