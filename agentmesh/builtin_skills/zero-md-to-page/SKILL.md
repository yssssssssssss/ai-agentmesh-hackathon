# zero-md-to-page

Turn one or more zero-md bundles into HTML display pages. The default output is the 商详大脑组件库规范页 style: restored spec board, hidden TOC, a single spec-page framework, canonical image slots for Relay cut images, and machine-readable drawer data. The audit output remains available when source coverage and quality status must be shown.

This skill is downstream of `zero-spec-to-md-skill`:

```text
zero-spec-to-md-skill: Zero design board -> zero-md specification bundle
zero-md-to-page-skill: zero-md specification bundle -> HTML display page / batch site
```

It does not read Zero design files, does not export screenshots, and does not write back to Zero. It only consumes the existing bundle files and renders them faithfully.

## Display Modes

### `brain` mode, default

Use this mode for component-library production pages.

- Render a JD Product Detail Brain style spec page.
- Prefer `raw/spec-page.json` when present. This is the authoritative visible-page contract: narrative blocks define the text flow, image-slot blocks mount existing Relay cut images, and covered child nodes remain trace-only.
- Fall back to screenshot assets from the zero-spec bundle when `raw/spec-page.json` is missing.
- Use `ancestorNodeIds` to render the highest successful tagged parent as a
  responsive composite board and keep covered child screenshots only in
  machine-readable traceability data when using the legacy screenshot fallback.
- Hide table of contents, quality reports, traceability, missing/pending details, and developer-only asset metadata from the visible frontend.
- Keep coverage markers and quality data in machine-readable output so validation still works.
- Emit `drawer-content.json` for 商详大脑二级抽屉嵌入, with screenshot mode as the default and D2C as the secondary display label.

### `audit` mode

Use this mode for internal review only.

- Show coverage summary, dev node records, screenshot statuses, component Markdown statuses, traceability, and quality report.
- Keep the original source-proving behavior from v1/v2.

## Output Contract

For a single bundle:

```text
{output}/
├── index.html
├── spec-page.html
├── drawer-content.json      # brain mode only, includes displayModes / specPage / screenshotSpec / structuredSpec
├── page-manifest.json
├── page-report.json
├── raw/
│   └── page-model.json
└── assets/
    └── screenshots/
```

For a batch site:

```text
{output}/
├── index.html
├── batch-manifest.json
├── batch-report.json
├── bundles/
│   └── {slug}.html
└── assets/
```

## Required Source Files

A complete source bundle should include:

```text
spec-narrative.md
design.md
rules.md
examples.md
traceability.md
_dev-nodes.md
raw/dev-nodes.json
raw/assets.json
raw/review-assets.json
raw/component-md.json
raw/workflow-state.json
_run.json
components-md/
assets/screenshots/
review-assets/screenshots/
```

Missing files must be reported in `page-report.json` and shown in the generated page. Do not silently skip missing content.

## Workflow

Single bundle:

```bash
python3 scripts/build_page.py {bundle} --output {output} --stage auto --display-mode brain
python3 scripts/validate_page.py {output} --stage auto
```

Reference-guided production page, when the user provides a target screenshot or asks AI to restore a reference style on top of the skill template:

```bash
python3 scripts/build_page.py {bundle} --output {output} --stage auto --display-mode brain --render-strategy reference-guided --layout-plan {layout-plan.json}
python3 scripts/validate_page.py {output} --stage auto
```

`reference-guided` must stay inside the normal builder. Do not overwrite
`index.html` or `spec-page.html` with ad hoc scripts. The layout plan may change
grouping, order, table/cell composition, and explanatory text placement, but it
must reference existing bundle image-slot `nodeId` values and keep all visible
assets declared by `raw/spec-page.json`.

Internal audit page:

```bash
python3 scripts/build_page.py {bundle} --output {output} --stage auto --display-mode audit
```

Batch:

```bash
python3 scripts/build_batch.py {root} --output {output} --stage auto
```

## Consistency Requirements

The page is trustworthy only if it can prove source coverage:

1. Every dev node in `raw/dev-nodes.json` appears in the page model and HTML.
2. Every dev node has screenshot status from `raw/assets.json` or `raw/review-assets.json`, depending on stage.
3. Every dev node has component Markdown status from `raw/component-md.json`.
4. Core Markdown files are rendered completely, not replaced by summaries.
5. HTML screenshot references come from the asset manifests, not guessed file paths.
6. Each component Markdown success record points to an existing file and matching frontmatter.
7. Missing, pending, failed, legacy, and mismatched records are visible in both page and report.
8. Every visual example card must expose screenshot status and a clickable `查看图片` route sourced from `resolvedRoute`, `path`, or `externalUrl`.
9. Batch generation may continue after one bundle fails, but the batch index must show that failure.

## Stages

Allowed page stages:

```text
auto
draft-page
review-page
final-page
```

`auto` maps from the source bundle workflow:

- visual review bundles -> `review-page`
- final bundles -> `final-page`
- everything else -> `draft-page`

Stage behavior:

- `draft-page`: screenshots may be pending, but pending state must be visible.
- `review-page`: use `raw/review-assets.json` and `review-assets/screenshots/`.
- `final-page`: use `raw/assets.json` and `assets/screenshots/`; pending final assets are errors.

## Page Sections

In `brain` mode, generated single-bundle pages should contain:

1. Sticky toolbar with return entry, component title, Relay/design/rules links.
2. Restored white spec board with the JD APP 16.0 guideline hero. In `brain` mode, render the unified UI2Code hero: left text content comes from the zero-md/page model title, owner remains `设计与用研部`, and the right decorative image uses multiply blending on the light board background.
3. Specification intro copied from the source bundle when available.
4. Sections restored from the source bundle structure, then enriched with matching rules and screenshots.
5. Spec-page image slots without visible node metadata; audit mode retains node ids and open-image links. Legacy bundles without `raw/spec-page.json` use screenshot-first responsive composite boards.
6. When an image slot carries `caption`, render it as the visible figure title above the image. Do not infer captions in the page renderer; consume the `raw/spec-page.json` contract from the bundle. Preserve grouped layouts from `slotGroupRole`, including horizontal section groups, scene grids, and vertical example lists.
6. Hidden machine-readable coverage markers for validation.

Do not visibly render TOC, quality report, traceability, dev container status, local absolute paths, or backend-only coverage diagnostics in `brain` mode.

When a bundle contains different domain structures, do not hardcode business section names. Build the outline from `raw/section-map.json` / `spec-narrative.md`, keep source order, attach `rules.md` content only when it is not already represented, and move content between sibling sections only on explicit heading-key matches.

In `audit` mode, generated single-bundle pages should contain:

1. Header: title, stage, quality status, source metadata.
2. Coverage summary: dev nodes, screenshots, component Markdown, source Markdown.
3. Specification narrative: full `spec-narrative.md` rendering.
4. Visual examples: every dev node with screenshot status and source metadata.
5. Component Markdown: every component-md record grouped by flavor.
6. Rules: full `rules.md` rendering.
7. Traceability: full `traceability.md` rendering.
8. Quality report: errors, warnings, pending and failed records.

Each visual example card should show the inline image when possible, the screenshot status badge, local asset path, absolute path when present, and a `查看图片` link that works even if the browser/Markdown renderer cannot inline the image.

## Validation

Use `references/page-quality-gates.md` when debugging validation failures.

Minimum passing state:

1. `page-manifest.json`, `page-report.json`, `raw/page-model.json`, and `index.html` exist.
2. Source files marked required are recorded in `page-manifest.json`.
3. Dev node coverage matches `raw/dev-nodes.json`.
4. Component Markdown coverage matches `raw/component-md.json`.
5. Screenshot coverage matches the stage-specific asset manifest.
6. `spec-narrative.md` is rendered in full when present.
7. Final pages do not have pending final assets.
8. All local screenshot references exist.
9. Every expected screenshot has a machine-readable HTML marker; every canonical
   visible image slot has a matching rendered image. Covered nested screenshots
   remain in `structuredSpec` / `specPage.trace` and do not require visible cards.
10. `page-report.json.status` is `pass` only when there are no errors.
11. Brain pages must keep `data-zero-md-page`, `data-render-strategy`, and
    `data-zero-page-fingerprint` markers generated by `build_page.py`.
    `validate_page.py` fails pages that were overwritten outside the builder.
12. When `raw/page-layout-plan.json` is present or `--render-strategy
    reference-guided` is used, `drawer-content.json.layoutPlan`, HTML image
    markers, and `raw/page-layout-plan.json` must agree.
