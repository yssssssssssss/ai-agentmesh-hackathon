## 模块一、真实痛点 / 使用场景提要

### 场景问题

**演示内容**：一张幻灯片，3 个场景短句 + 1 张"信息在流动但没有沉淀"的总结句。

**口播内容**：
> "先问大家一个问题：如果你们团队去年做过的项目，今天新来的同事完全不知道，你觉得损失有多大？
> 我们观察到三类真实场景：**经验流失**——'去年 618 家电会场做过什么方案？效果如何？'只能翻聊天记录，运气不好就是重新踩坑；**多源割裂**——数据在 BI，竞品资料靠人肉搜索，风险规则压在法务文档里，一个问题要开 4 个系统；**审批黑洞**——AI 帮你干活，但高风险操作到底谁签字，现在大部分方案是'AI 自己决定'或者'全靠邮件'。这三个问题的共性是：**信息在流动，但没有沉淀；能力在增强，但没有治理。**"

### 解决方案

**演示内容**：一句话产品定位卡片——"数字员工不是一个人，而是覆盖工作全生命周期不同阶段的一组数字员工"。

**口播内容**：
> "AgentMesh 的出发点很简单：**数字员工不是一个人，也不是一套流程里的某个角色，而是贴合一次工作生命周期、在不同阶段接力上场的一组数字员工**——有人帮你找资料，有人帮你查数据，有人帮你审风险，还有一个一直在后台，把这些过程沉淀成个人、项目、团队的记忆和能力。这也是我们和市面上大多数单 Agent 工具最大的区别：别人在做"一个更强的助手"，我们在做"一套会协作、会记忆、有治理的数字员工体系"。"

### 项目演示

**演示内容**：不单独演示，作为后续 5 个模块 demo 的预告——展示一张"6 个模块 → 对应页面"的路线图（真实痛点→架构图→Workspace 聊天→我的知识/工作洞察→协作/协作市场→总结）。

**口播内容**：
> "接下来的每一个模块，我们都会现场打开真实页面、跑真实操作，不是讲 PPT，是讲代码。"

### 技术架构

**演示内容**：不涉及技术细节，跳过或用一句话过渡。

**口播内容**：

## 模块二、整体架构

### 场景问题

**演示内容**：对比图——"单一通用 Agent"（一个框，什么都塞）vs "AgentMesh 多 Agent 协作"（多个专业角色 + 共享看板）。

**口播内容**：
> "如果只有一个通用 Agent 什么都干，会遇到两个问题：一是它没法针对性地被授权/被信任做某类操作，二是任何一个环节挂了，整条链路就断了。我们需要的是可插拔、可审计、能异步协作的架构。"

### 解决方案

**演示内容**：架构图——聊天入口 → FastAPI 路由 → Personal Agent 调度 → Research/Data/Risk Agent → Blackboard（共享看板）→ SQLite 持久化。

**口播内容**：
> "AgentMesh 是一个 chat-first 的团队 Agent 协作平台。用户只面对一个聊天窗口，输入 `$` 唤起技能菜单——查记忆、发起调研、查数据、审风险、沉淀经验——背后是 Personal Agent 调度 Research/Data/Risk 三个专业 Agent，通过一个叫 Blackboard（黑板）的共享看板异步协作，而不是互相硬编码调用。"

### 项目演示

**演示内容**：在 Workspace 聊天里输入 `$system.info`，现场展示当前用户可用的模型配置和 Skill 列表；如果时间够，打开 `/docs` Swagger 页面展示真实 API 路由分组（chat / memory / market / knowledge / inbox 等）。

**口播内容**：
> "`$system.info` 这条命令背后没有特殊逻辑，它跟其他 10 个 Skill 走的是同一套路由表（`agentmesh/chat_skills.py`，一共 11 个 `ChatSkillSpec`）——这说明我们的'菜单'不是前端硬编码的按钮，是后端统一注册、可扩展的技能表。"

### 技术架构

**演示内容**：代码片段/文件路径清单——`agentmesh/chat_skills.py`（11 个技能定义）、`agentmesh/agents.py`（PersonalAgent 调度逻辑）、`agentmesh/marketplace.py`、`agentmesh/models.py`（Blackboard 7 种 post 类型：request/evidence/risk/digest/decision/correction/memory_candidate）。

**口播内容**：
> "Blackboard 不是消息队列，是一张带类型的共享看板，7 种 post 类型覆盖了从'提需求'到'留证据'到'下决策'的完整协作语义；执行锁保证同一时刻不会有两个 Agent 抢着写同一条任务，这是我们能做到'任何一个 Agent 挂了不影响其他人'的根本原因。"

## 模块三、个人能力拓展

### 场景问题

**演示内容**：一句话卡片——"AI 拓展了个人能力，但如何保证答案有来源、高风险操作有人审？"

**口播内容**：
> "AI 工具带来了团队和个人能力的极大赋能，这也是市面上大多数 Agent 工具在做的事情，但我们要更进一步：能力拓展之外，还要**可信**（不编造，有来源）和**可控**（高风险操作不能 AI 自己拍板）。"

### 解决方案

**演示内容**：一张"能力入口"图——聊天里的 `$research.request`（请求外部资料）和 `$risk.review`（风险/授权检查）两个真实 Skill，及其背后对应的 Research Agent / Risk Agent。

**口播内容**：
> "个人能力的载体不是一个单独的'能力配置页'，是聊天里的 `$skill` 路由——你不需要去学一套新界面，只要在聊天框里打 `$` 就能看到自己能用的能力。这一点跟很多产品把'能力设置'做成一个专门的后台页面不一样，我们刻意让它保持 chat-first。"

### 项目演示

**演示内容**：
1. 在 Workspace 聊天里输入 `$research.request 查找去年 618 家电会场的复盘经验`，展示返回结果**带来源**（source）。
2. 输入 `$risk.review 检查这批外部素材授权风险`，触发风险检测。
3. 切到"我的知识"页面的"待处理"Tab（或者从 DigitalSelf 首页"数字员工动态"里的待处理卡片点进去），看到刚才那条 `prompt_injection_review` 类型的项（图标是警示盾，和普通的团队候选记忆区分开），点击"释放"或"丢弃"完成人工确认。

**口播内容**：
> "这一步不是在演示一个聊天机器人，是在演示——**一次真实工作生命周期里，不同阶段对应不同的数字员工接力上场**：调研的时候是 Research Agent，查风险的时候是 Risk Agent，而且每一步都有来源、有审计。风险检查生成的项不会自己消失，也不会自己被 AI 处理掉，它会进'我的知识'页面的待处理列表，等人来确认——这是 Human-in-the-Loop 闭环，AI 不越权。
> 顺带说明一下：如果大家想看'这个用户的 Agent 被授权了哪些工具'，那个列表目前在 DigitalHuman 页面的'能力与 Skill'区块里，但**如实告知**——那块目前是参考 UI，数据是前端 Mock 的 `CONFIGURED_SKILLS`，真正决定'这个用户能用哪些能力'的，是刚才展示的聊天里那 11 个 `$skill` 命令，这个是真实生效的。"

### 技术架构

**演示内容**：代码片段——`chat_skills.py` 里 `$research.request`（第 99 行）和 `$risk.review`（第 117 行）的 `ChatSkillSpec` 定义；`InboxItem` 数据结构；提示注入检测逻辑位置。

**口播内容**：
> "外部资料先过提示注入检测，可疑内容不会直接喂给 LLM，会被标记为 needs_review 转人工——这条链路和'我的知识'待处理列表是同一套 Inbox 机制，只是不同 `itemType` 展示不同的处理按钮（团队候选记忆是'接受'，风险审查项是'释放/丢弃'）。"

## 模块四、记忆模块（个人 / 项目 / 团队三级记忆 + 工作流程 Skill 提炼）

> 这是全场技术纵深最重的模块，工程量真实存在（P0-P4 + A1-A3 + R1-R2 + C1，全部有对应 commit）。前端把这套记忆系统拆在**"我的知识"和"工作洞察"两个页面**里，demo 要来回切两个页面才是完整的记忆系统。

### 场景问题

**演示内容**：一句话卡片——"记忆内容越多，越难被好好利用"。

**口播内容**：
> "感谢 AI，我们现在可以同时做很多事情，有大量的产出，可以将各类数据沉淀为知识。但同时也带来问题——我们在单位时间内制造了越来越多的内容，但并没有好好利用这些内容。记忆内容变得越来越多，但也越来越难被好好利用。需要一个地方能把所有内容整合起来，而这正是这套记忆系统的核心。"

### 解决方案

**演示内容**：分层示意图——`Scope`（private / project / team_candidate / team_accepted）+ `MemoryLayer`（short_term / mid_term / long_term）双维度矩阵；旁边标注"leader 可直接给团队/项目提供记忆，普通成员的候选记忆需审核后才能进团队记忆"。

**口播内容**：
> "这里会有个人、项目、团队三层记忆系统，可以把团队能力放到最大：leader 可以直接给 team、project 提供 memory；普通用户产出的记忆，需要先经过确认，才能同步给 team、project；每个用户还会有一个 Agent，每天检索他的日常记忆并生成总结，供用户决策是否要同步到更高层级。这不是简单的'数据库分区'，是一套**记忆治理**——按 `team_id` 隔离（A3，已完成），同一工作区不同团队互不可见，避免'记忆越多越乱'。"

### 项目演示

**演示内容**：
- **A. "我的知识"页面·待处理 Tab**：选一条团队候选记忆，点击"接受"——真实的 `acceptMemory` mutation，成功后提示"团队候选已接受并进入共享知识"。
- **B. 切到"工作洞察"页面**：展示三层记忆统计卡片（short_term / mid_term / long_term 各自条数，来自真实接口 `/api/memory/overview`）；再展示"知识提炼"卡片（当前这块卡片数据是**参考展示（M）**，如实说明）。
- **C. 口播补一句，不用切页**：现场用 curl 或打开 `/docs` Swagger 调一次 `/api/search`，证明语义检索接口是真实跑通的。

**口播内容**：
> "第一步展示的是**记忆治理**：只有组长/管理员能把候选接受为团队记忆，且按团队隔离。第二步的三层统计是真实数据，对应'分层'——短期是今天做了什么，中期是项目级提炼，长期是团队级沉淀。第三步的'知识提炼'卡片，目前前端用的是参考数据，但**真正的判定逻辑是真实跑的**——同一种工作模式（比如'查项目部署状态'）重复出现 3 次以上且都成功，`agentmesh/skill_extractor.py` 会自动提炼成一条 LearnedSkill，下次同类请求直接按已验证步骤执行，而不是重新推理一遍。这一句直接对应我们原始立意里'会有一个 agent 自动总结用户的解决问题的思路，并沉淀为 skill'——是真实已实现的能力，只是这块前端卡片还没接到真实检测结果，我们现场打开代码或跑一次对应测试来证明。
> 检索用的不是简单字符串匹配，是 FTS5 全文检索 + 向量语义检索（Qwen3-Embedding）用 RRF 做混合排序——'去年搜"部署失败"搜不到"发布异常"，现在能搜到，因为做了语义层。'这个接口后端已经跑通、有测试覆盖，前端搜索框还没接线，我们更愿意告诉大家真实进度，而不是演成已经全部连好。"

### 技术架构

**演示内容**：一张 roadmap 完成清单——P0 FTS5 全文检索、P1 SearchBudget、A1 个人→项目共享、A2 member_ids 校验、P2 Qwen3-Embedding + RRF 混合检索、R1 分层检索策略（TEAM→PROJECT→PRIVATE）、A3 team_id + TeamMembership 隔离、R2 citation_rate + 延迟指标、P3 bigram 模式识别 + LearnedSkill 自动提炼（阈值≥3）、P4 AgentMemoryBinding、C1 文档→长期记忆自动导入——全部标注对应 commit。

**口播内容**：
> "三层记忆 + FTS5 全文检索 + 向量混合排序（RRF）+ Skill 自动提炼（P3）+ Agent 精准装备（P4）——这是这个项目里工程量最大、最能体现'不是在套壳 ChatGPT'的部分，评委大概率会追问'记忆系统怎么做的'，我们可以逐条对应代码文件回答。个人和项目、团队记忆的关系上，我们没有沿用'ERP+C3 冻结时间点'那套复杂身份体系——现在代码里是本地 session + workspace/project/team_membership，没有'冻结'逻辑，这是我们对原始方案做的诚实简化，讲出来经得起追问。"

## 模块五、Agent 互助模块

### 场景问题

**演示内容**：一句话卡片——"数据不能只是被动存起来等你来查，还要能主动流动起来"。

**口播内容**：
> "当我们有了更强的能力，能够在单位时间内做更多的事情，除了把它们存起来成为固定资产（被动访问），我们还要有流动资产——让数据自动流动起来，让 Agent 之间能互相发现'谁能帮谁'。"

### 解决方案

**演示内容**：流程图——Agent-1（自动巡检+发布求助信号到 BBS）→ Blackboard `MARKETPLACE_SIGNAL` → Agent-2（自动扫描+匹配+代答）→ 采纳后记一条 `ContributionPoint`。旁边标一个 opt-in 开关图标。

**口播内容**：
> "我们给项目增加了自动巡检的 agent：一个会自动检查你在做的项目有哪些需要帮助，并创建求助贴发布到 BBS 上；另一个自动在 BBS 上检查有哪些求助是'自己'可以解决的，主动去提供资料、解决方案。这套流动资产互助系统，目前已经有奖励机制的雏形驱动——谁帮了谁、帮了多少次，代码里已经在真实记录。"

### 项目演示

**演示内容**：
1. 打开 Collaboration（协作）页面，展示 Market Board 和"加入市场/退出市场"opt-in 开关，以及"市场参与者"计数。
2. 展示一次提前手动触发好的真实匹配：agent-1 发布的求助信号 + agent-2 生成的代答，在时间线里配对出现。
3. 切到 Market（协作市场）页面——这是"我"这个用户的个人视角时间线：我发出的求助、我收到的回答、我给别人的回应，一次呈现。
4. 现场打开 Python shell，调用一次 `store.list_contribution_points()`（或直接看代码 `agents.py:1495` `adopt_delegated_answer`），证明求助被采纳后确实记了一条 `ContributionPoint`。

**口播内容**：
> "Collaboration 页面看到的是**组织级看板**——所有参与者的信号和匹配都在这；Market 页面看到的是**我自己的视角**——我的分身在市场里发出的求助、收到的回答、给别人的回应。这套机制默认不是全局广播，用户可以自主决定是否让自己的 Agent 参与，尊重隐私边界。当求助方采纳了对方的代答，系统会给回答者记一条 `ContributionPoint`——record-only 的贡献点，这是'活跃度被记录'的雏形，只是目前**没有排行榜/兑现规则/公开 API**，我们现场用代码证明'已经在记'，而不是空口说。"

### 技术架构

**演示内容**：代码片段——`agentmesh/marketplace.py` 的 `publish_all_signals(store)` / `scout_all(store)`（已测试的 step 函数）；`routes/market.py`；`MarketParticipation` opt-in 模型；`models.py:586` 的 `ContributionPoint`；`agents.py:1495` 的 `adopt_delegated_answer`（同时生成 `MemoryRelation` derived-from 边）。

**口播内容**：
> "`publish_all_signals` 和 `scout_all` 是两个已测试的 step 函数，不依赖真实等待周期，我们提前手动调用过一次，所以台上看到的匹配是真实数据，不是提前录好的动画。`adopt_delegated_answer` 这一步很关键——它不只是记一个贡献点，还会给采纳方生成一条 `UserMemoryItem`（来源标记 `delegated_answer`）和一条 `MemoryRelation`，也就是说，互助行为本身也会反哺回记忆系统，这是模块四和模块五真正打通的地方。"

**口播内容**：
> "通用 ChatBot 只能聊；企业知识库只能被动搜；AgentMesh 是**聊天优先 + 多 Agent 协作 + 记忆主动沉淀 + 风险人工在环**——这四个加在一起，才是团队真正需要的'AI 工作大脑'，不是又一个问答框。"

### 解决方案

**演示内容**：工程质量清单——551 个自动化测试全绿；带真实 checklist（来源、证据帖、权限、关键词覆盖）的评测数据集；`provider_smoke.py --embedding --o2 --web --data --llm` 真机验证结果。
