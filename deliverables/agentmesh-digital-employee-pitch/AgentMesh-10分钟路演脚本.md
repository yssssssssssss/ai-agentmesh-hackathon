## 0. 我对你原始脚本的调整说明（先读这一段）

你给的 `hackathon-脚本-0.md` 的立意——**"数字员工不是一个人，而是覆盖工作全生命周期不同阶段的一组数字员工"**——这个开场判断非常好，我保留并把它作为整场路演的主线。但三处做了调整，原因如下：

1. **去掉 ERP+C3 身份体系、"项目记忆在用户变更时间点冻结"的表述**：现在代码里的身份是本地 cookie-session + workspace/project/team_membership，没有 ERP/C3 绑定，也没有"冻结"逻辑。这两处如果讲出来，懂技术的评委一问代码就穿。改成讲实际存在的 `Scope`（private/project/team_candidate/team_accepted）+ `team_id` 隔离（A3，已完成）。
2. **互助市场的"奖励机制驱动"保留，但按代码里实际的粒度讲**：BBS 自动发布求助信号（agent-1 publisher）、自动匹配并解答（agent-2 scout）**都已经真实实现**（`agentmesh/marketplace.py`），这是你脚本里最值钱的一段，我把它放大讲了；"奖励机制"这一层，代码里已经有 `ContributionPoint`（`models.py:586`）——B 采纳 A 的代答时会给 A 记一条 record-only 的贡献点（`agents.py:1495` `adopt_delegated_answer`），这就是"活跃度被记录"的雏形，只是目前**没有排行榜/兑现规则/公开 API**，我把这部分放进 Demo 三里用代码/数据证明"已经在记"，把"排行榜和兑现"放进 One more thing 里诚实讲成下一步。
3. **"团队记忆的记忆系统"这段，我建议用实际已完成的技术深度替换掉抽象描述**：三层记忆（short/mid/long）+ FTS5 全文检索 + 向量混合排序（RRF）+ Skill 自动提炼（P3）+ Agent 精准装备（P4）——这是这个项目里工程量最大、最能体现"不是在套壳 ChatGPT"的部分，评委大概率会问"记忆系统怎么做的"，值得单独给 90 秒技术纵深。

其余结构基本沿用你的三段式（个人能力拓展 → 记忆系统 → agent 自动化），但补齐了 Demo 环节——黑客松路演如果 10 分钟里没有 3 分钟以上的真实操作演示，说服力会明显打折。

## 逐段脚本（总时长 10:00）

### 第 1 段·开场钩子（0:00 - 0:30）

> "先问大家一个问题：如果你们团队去年做过的项目，今天新来的同事完全不知道，你觉得损失有多大？
>
> AgentMesh 的出发点很简单：**数字员工不是一个人，也不是一套流程里的某个角色，而是贴合一次工作生命周期、在不同阶段接力上场的一组数字员工**——有人帮你找资料，有人帮你查数据，有人帮你审风险，还有一个一直在后台，把这些过程沉淀成个人、项目、团队的记忆和能力。"

**要点**：直接抛出你原脚本的核心立意，作为区别于"又一个 ChatBot"的钩子。

### 第 2 段·真实痛点（0:30 - 1:30）

用 3 个具体场景代入，不要抽象讲"效率低"：

- **经验流失**："去年 618 家电会场做过什么方案？效果如何？"——现状是翻聊天记录、翻文档，运气好能找到，运气不好就是重新踩坑。
- **多源割裂**：数据在 BI 平台，竞品资料靠人肉搜索，风险规则压在法务文档里，一个问题要开 4 个系统才能回答完。
- **审批黑洞**：AI 帮你干活，但高风险操作（批量抓取、素材授权、内网访问）到底谁签字？现在大部分方案是"AI 自己决定"或者"全靠邮件"。

一句话收尾："这三个问题的共性是——**信息在流动，但没有沉淀；能力在增强，但没有治理。**"

### 第 4 段·Demo 一：个人能力拓展（2:00 - 4:00，2 分钟）

按你原脚本"一、个人能力的拓展"的立意，现场跑一遍最短闭环：

1. 打开 DigitalSelf（数字自己）页面，展示这个用户的 Agent 配置——名字、模型、被授权的工具（工具是显式按 Agent 授权的，不是全局暴露）。
2. 在聊天里输入 `$research.request`，问一个提前准备好、demo 数据里有答案的问题（比如"去年 618 家电会场的复盘经验"）。
3. 展示返回结果**带来源**（source），强调"不编造，只基于给定上下文回答"。
4. 再跑一次 `$risk.review`，展示一条素材授权问题被自动路由到收件箱（Inbox），等待人工确认——这是 Human-in-the-Loop 闭环，AI 不越权。

**口播**："这一步不是在演示一个聊天机器人，是在演示——**一次真实工作生命周期里，不同阶段对应不同的数字员工接力上场**：调研的时候是 Research Agent，查风险的时候是 Risk Agent，而且每一步都有来源、有审计。"

### 第 5 段·Demo 二：记忆系统（4:00 - 6:30，2.5 分钟，全场技术纵深最重的一段）

这段的工程量是真实存在的（P0-P4 + A1-A3 + R1-R2 + C1，全部有对应 commit）。前端目前把这套记忆系统拆在**"我的知识"和"工作洞察"两个页面里**，要连起来看才是完整的记忆系统——所以这段 demo 要来回切两个页面：

**A. "我的知识"（Knowledge）页面**

1. **待处理 Tab**：选一条团队候选记忆，点击"接受"——这是真实的 `acceptMemory` mutation，成功后提示"团队候选已接受并进入共享知识"。这一步同时展示了**记忆治理**：只有组长/管理员能把候选接受为团队记忆，且按 `team_id` 隔离（A3，已完成，同一工作区不同团队互不可见），避免"记忆越多越乱"。

**B. 切到"工作洞察"（Insights）页面**

2. **三层记忆统计卡片**：short_term / mid_term / long_term 各自的条数，这是真实数据（来自 `/api/memory/overview`），对应"分层"——短期是今天做了什么，中期是项目级提炼，长期是团队级沉淀。
3. **"知识提炼"卡片**：这里展示的是"重复模式建议沉淀为 Skill"的交互长什么样，目前这块卡片用的是参考/演示数据，如实说明；但**真正的判定逻辑是真实跑的**——同一种工作模式（比如"查项目部署状态"）重复出现 3 次以上且都成功，`agentmesh/skill_extractor.py` 会自动提炼成一条 LearnedSkill，下次同类请求直接按已验证步骤执行，而不是重新推理一遍。**这一句直接对应你原脚本"会有一个 agent 自动总结用户的解决问题的思路，并沉淀为 skill"，是真实已实现的能力，只是这块前端卡片还没接到真实检测结果，我们现场打开代码或跑一次对应测试来证明。**

**C. 口播补一句（不用切页）**：这套记忆系统检索用的不是简单字符串匹配，而是 FTS5 全文检索 + 向量语义检索（Qwen3-Embedding）用 RRF 做混合排序——"去年我们搜'部署失败'搜不到'发布异常'，现在能搜到，因为做了语义层。"这个 `/api/search` 接口后端已经跑通、有测试覆盖，前端搜索框还没接线（`useSearchQuery` 这个 hook 已经写好，只是还没有页面调用它），我们现场用一次 curl 或打开 `/docs` Swagger 证明它是真的，不是画饼。

**口播收尾**："记忆内容越多越难利用，这是你们大概都遇到过的问题。我们做了四件事：**分层**（短中长期，工作洞察页能看统计）、**治理**（候选要审核才能进团队记忆，且按团队隔离）、**语义检索**（FTS5+向量+RRF，接口已跑通）、**提炼**（重复模式自动变成可复用技能，逻辑已跑通）。后两件事前端还在接线，我们更愿意告诉大家真实进度，而不是演成已经全部连好。"

### 第 6 段·Demo 三：Agent 自动化互助市场（6:30 - 8:00，1.5 分钟）

对应你原脚本"三、agent 自动化"里最亮的一段，且是**真实已上线**的功能（`agentmesh/marketplace.py` + `routes/market.py`）：

1. **打开 Collaboration（协作）/ Market 页面**，展示 Market Board：每个开启参与的用户，其个人 Agent 会定期把"我最近在做什么、可能需要什么帮助"发布成一条 `MARKETPLACE_SIGNAL` 到 BBS。
2. **展示一次真实匹配**（提前手动触发好的那次）：另一个用户的 Agent（agent-2 scout）自动扫描看板上的求助信号，发现自己手里有相关资料/经验，主动生成一条回答，双方 Agent 之间形成一次"匹配 → 应答"的记录，进入时间线。
3. **展示 opt-in 开关**：这套机制默认不是全局广播，用户可以自主决定是否让自己的 Agent 参与这套互助市场——尊重隐私边界。
4. **展示奖励机制的雏形**：当求助方采纳了对方的代答（`adopt_delegated_answer`，`agents.py:1495`），系统会给回答者记一条 `ContributionPoint`（`models.py:586`）——这是 record-only 的贡献点，谁帮了谁、帮了多少次，代码里已经在真实记录。这块目前没有公开 API/UI，现场打开 Python shell 调一次 `store.list_contribution_points()`，或者直接看代码，证明"活跃度被记录"不是空话。

**口播**："这一步是我们脚本里说的'流动资产'——数据不能只是被动存起来等你来查，还要能主动流动起来，让 Agent 之间互相发现'谁能帮谁'。贡献点已经在记录了，还没做的是把它变成看得见的排行榜和可兑现的奖励规则，我放在最后的 One more thing 里诚实讲。"

### 第 7 段·为什么这事难 / 技术亮点（8:00 - 9:00）

快速过 4 个亮点，每个 10-15 秒，不展开代码：

1. **Blackboard 架构**：Agent 之间不是硬编码互相调用，而是通过共享看板异步协作，任何一个 Agent 挂了不影响其他人，新 Agent 接入不用改核心逻辑。
2. **Protocol 边界 + 真实内网打通**：外部依赖（搜索、数据、LLM）全部走接口边界，可插拔；我们不是纯 mock 演示——`research_agent`/`data_agent` 已经对接了京东内部 Oxygen-CLI（metasearch/o2-kb/oxygen-comment/bdp-copilot），并且拿真机做过命令契约验证。
3. **风险与审计**：外部内容先过提示注入检测，可疑内容不直接喂给 LLM，标记为 needs_review 转人工，每个操作都有 AuditEvent 全链路留痕。
4. **工程质量**：551 个自动化测试 + 一套带真实 checklist（来源、证据帖、权限、关键词覆盖）的评测数据集，不是"能跑起来就行"的原型。

### 第 9 段·One more thing / 诚实的愿景（9:20 - 9:50）

> "今天讲的是给**个人**建数字画像。下一步，我们想把这套画像能力扩展到**项目**和**合作方**——项目也可以有自己的数字画像，业务项目讲'我做了什么营销设计、CTR 涨了多少，你要不要试试'，技术项目讲'我做了什么性能优化、压测踩过什么坑，我们一起进化'。
>
> 互助市场今天已经能自动发现'谁需要帮助、谁能帮'，也已经在给帮忙的人记贡献点（`ContributionPoint`）。还没做的是把这些点数变成**看得见的排行榜和可兑现的奖励规则**——谁的 Agent 越活跃、贡献越多，怎么给到对应的回报，这是我们清楚知道、也已经有数据基础，但今天还没做完整 UI 的下一步，不装作已经做完。"
