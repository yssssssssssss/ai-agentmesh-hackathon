# 项目巡检到处理行动与经验复用：开发计划

- 日期：2026-10-07。
- 状态：待实施。本文记录下一步的具体开发范围，不表示下列新增入口已经完成。
- 上位方案：[AgentMesh 完整优化方案](2026-10-04-agentmesh-complete-optimization-plan.md)，重点落实第 3、9 节的「查询 → 巡检 → 确认行动 → 沉淀经验」。
- 既有闭环：[独立任务与记忆闭环开发计划](2026-08-31-standalone-task-memory-closed-loop-development-plan.md)。本次补齐巡检到处理的入口和来源关系，沿用已有任务、执行、审核及记忆能力。
- 约束：[ADR 0016](../adr/0016-trusted-query-and-manual-project-inspections.md)、[ADR 0042](../adr/0042-committed-project-change-inspections.md)；巡检保持只读，用户确认后的写操作仍由现有 Task/Review 命令完成。

## 1. 要解决的问题与直接收益

当前用户可以看到阻塞、逾期、依赖未完成和长期未更新的任务，也可以打开任务详情。但巡检结果尚未提供明确的处理入口；独立跟进任务与当时发现的问题也没有专用来源记录。任务验收、经验捕获和后续复用已经存在，入口之间仍需用户手动衔接。

| 用户遇到的情况 | 本次交付后的行为 | 直接收益 |
| --- | --- | --- |
| 巡检发现某个任务阻塞 | 从结果打开原任务的当前管理界面，核对原因、依赖、负责人和可执行操作 | 减少重新查找任务和整理处理背景的步骤 |
| 解决阻塞需要单独调研或修复 | 生成带问题背景和来源引用的可编辑跟进草稿，明确确认后保存 | 减少复制信息和交接遗漏，保留「为什么创建这个任务」 |
| 想知道问题有没有解决 | 从来源任务查看跟进任务及其交付阶段、Run 和 Review | 将问题与实际处理结果关联，减少重复询问进度 |
| 某次处理形成有效方法 | 从已验收交付显式捕获经验，经相应审核后供后续任务使用 | 让下一次类似工作有方法、适用条件和结果证据可查 |

上述收益是产品预期。现有代码能证明基础能力存在，尚不能证明团队节省了多少时间；本文不承诺百分比、商业效果或模型质量提升。第一批试点记录发现到确认处理的用时、人工整理步骤和一次后续复用结果即可，不增加独立统计平台。

## 3. 用户流程与范围

1. 用户运行巡检，或打开自己有权访问的自动巡检报告。
2. 在「需关注的任务」中点击「处理此问题」，读取原任务当前详情。界面展示巡检时的问题与当前状态；来源已变化时提示重新核对。
3. 默认处理原任务：按当前允许操作编辑、分派、调整计划或处理阻塞。查询与打开表单不产生任务变更。
4. 只有需要独立交付时，用户选择「创建跟进任务」。表单预填问题背景，用户补充目标、负责人、截止时间和验收要求，再确认保存。
5. 用户按已有流程计划、启动任务或 Agent Run，提交产物并请求交付审核。
6. 交付验收后，用户显式捕获经验。个人经验保持私有；团队候选通过独立 Memory Review 后才能成为团队知识。
7. 在下一次任务中查询或选择可用方法，生成草稿；实际执行仍经过当前权限、适用条件和来源检查。

第一批新增处理操作仅覆盖报告中的阻塞、依赖、逾期、长期未更新事项。进展变化继续链接来源；待审核事项进入现有审核流程，不复制成新任务。写入模式关闭或用户缺少操作权限时，保留来源查看并说明当前无法处理。

来源关联不会自动改变任务父子关系或执行依赖。只有用户确实需要任务拆分或依赖门禁时，才显式使用现有关系编辑。完成跟进任务也不会自动解除原任务阻塞或证明原问题已解决；以原任务当前状态和相应审核为准。

## 4. 实现设计

### 4.1 入口与客户端草稿

- `ProjectInspectionView` 增加处理回调，由任务页面绑定现有管理入口；自动报告页面复用同一组件。
- 打开后读取服务端当前 Task 详情与允许操作。报告中的标题、原因和时间是历史背景，不决定当前可写权限。
- 草稿带项目 ID、来源任务 ID/版本、原因码和可编辑目标/说明。来源版本从报告 `evidence_refs` 的 Task 引用读取，不能假设 blocker 本身有 `version` 字段。
- 没有可靠版本时，先重新读取当前详情；不以缺失的历史版本确认来源。切换账户、Workspace 或项目后清除旧草稿和表单。
- 复用现有 `TaskFormDialog`，草稿正文放在客户端状态中，URL 只带导航所需的项目/任务身份。链接访问不自动保存、启动或执行记忆步骤。

### 4.2 跟进任务的最小来源记录

拟在现有 Task 管理元数据中增加一个可选、不可由普通编辑改写的 `inspection_origin`，不建立新 Issue 聚合或处理状态机。创建请求只提供来源任务、预期版本及所选风险原因；持久记录由服务端核对后生成，至少包含：

| 字段 | 用途 |
| --- | --- |
| `source_task_id` | 回查原任务 |
| `source_task_version` | 标识确认创建时核对的版本 |
| `reasons` | 经当前任务规则核对的风险原因码 |
| `recorded_at` | 服务端确认来源的时间 |

原始巡检时间可作为界面背景展示，不作为服务端执行证明或授权依据。普通创建请求不带来源时，保持旧的行为、序列化结果和命令 hash。实现时使用有界 Pydantic 类型，避免任意字典成为新的事实通道。

创建沿用 `TaskManagementService` → `SQLiteStore.create_managed_task`。在原写事务内核对当前用户、项目、来源 Task 的共享任务范围、可见性、有效状态和预期版本，并复用确定性风险规则检查所选原因仍成立。权限撤销、来源归档或已变化时不创建，返回可理解的原因，让用户刷新后重新确认。

来源、Task、Thread、命令回执和审计一次提交，失败全部回滚。重复传输使用同一 `command_id` 和请求 hash，只返回原创建结果；同一命令改变项目或来源产生冲突。主动创建另一项跟进允许使用新命令，界面展示已有跟进供用户判断，不能将每种风险强制限制为一个任务。

来源详情展示当前可访问的跟进任务，跟进详情提供来源回查。沿用现有分页和权限过滤；来源后来不可访问时仅显示「来源当前不可用」，不回显缓存标题或正文。此关系用于追溯，不授予来源/产物的读取权限。

### 4.3 审核、记忆与状态解释

- Task Review 继续冻结 Run 与产物证据；审核通过不自动发布团队知识。
- 复用现有经验捕获表单与 API，在有效的已验收交付上提供清晰入口；无审核证据时解释缺口。
- 捕获方法保留目标、前置条件、环境/工具版本、步骤、验证条件和真实结果依据。普通摘要不能冒充可执行方法。
- 任务详情串联来源、处理任务、交付审核与记忆链接。当前状态查询走 SQL；历史经验走 Memory，各自显示来源与时间。
- 方法草稿和查看记忆不算模型使用。实际交付上下文后沿用已有精确使用回执；新任务质量仍由产物与独立审核判断。

## 5. 开发顺序与可交付结果

| 顺序 | 开发内容 | 独立可用的交付结果 | 主要改动位置 |
| --- | --- | --- | --- |
| A | 巡检处理按钮、当前来源核对、进入原任务管理 | 用户从手动/历史巡检直接处理原任务 | `ProjectInspectionPanel.tsx`、`AutomationSchedulePanel.tsx`、`Tasks.tsx` |
| B | 跟进草稿、服务端来源校验、原子创建、双向来源展示 | 独立跟进有背景和可回查关联，重复提交不会重复创建 | `TaskFormDialog.tsx`、任务 API/types、`models.py`、TaskManagement contracts/service、Store |
| C | 处理结果、审核与经验捕获/复用的连续导航 | 用户能找到证据、保存经验并进入下一次任务 | Task 详情/表单、Knowledge 详情，复用既有 Task/Memory Review |
| D | 用一条真实项目问题走完整流程并整理实际反馈 | 证明这些入口可以协同完成工作，记录尚未解决的产品缺口 | 试点记录和总方案进度 |

先交付 A，再实施需要持久写入的 B。C 只补缺失入口与上下文衔接；现有审核、捕获和复用已满足要求时直接复用。完成一个切片即可交付其用户价值，不将四个切片合成一次大重构。

沿用 FastAPI、React、SQLite、Task/Review、Runtime 和 MemoryContextService。本次没有新数据库、图引擎、消息队列、Agent 框架或外部写回连接器的开发需求。新增代码围绕来源校验和页面衔接收敛，风险规则与已有巡检共用，避免另写一套判断。

## 6. 必要验证与完成标准

日常只检查新行为和直接受影响的边界：

- A：正确项目/Task 打开，当前权限与历史报告变化提示，账户/项目切换清理。
- B：正常创建、相同命令重放、改变来源冲突、无权限/跨项目/旧版本拒绝，以及一次写失败的完整回滚。
- C：仅有效审核证据可捕获、团队独立审核仍生效、旧经验不会绕过当前适用性与来源检查。既有未改动的完整链路不重复扩展测试。
- 前端/契约变化运行必要类型检查和受影响静态检查；切片通过后继续开发。整体交付时走一次界面流程，失败才针对性修复和复查。

本次完成必须能展示：真实巡检问题 → 打开并核对原任务 → 确认处理或创建有来源的跟进 → 显式执行 → 带产物的交付审核 → 显式捕获经验 → 下一次任务查询/草稿/符合条件时使用方法。只完成按钮或模拟回执不算全部交付。

本项目的真实问题优先作为试点，资料和 GitHub Issue 可经已有读取/导入能力进入项目；外部 Issue 状态不自动成为本地 Task 状态。无需先接入新的企业系统才能开发入口。真实 Agent 产物质量和团队采用收益需在有效 Provider 与真实使用中单独记录，确定性 SDK 检查不能替代这些结论。
