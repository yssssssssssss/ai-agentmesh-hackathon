# ADR 0065: Runner context admission and confirmed delivery

Status: Accepted, implemented 2026-10-07.

New CLI Runners advertise `context-handoff-v1`. V3 execution envelopes reuse the existing private SDK Session and prepared Run context snapshots for direct execution and Standard Skill nodes. Claiming work prepares context without recording Memory usage. Legacy envelopes keep their hash contracts and do not receive newly prepared automatic Memory or core preferences.

Before each SDK model request, including compaction and turns after tool results, the Runner checks the complete request budget and obtains an authenticated cloud handoff. The control plane checks the active lease, Run writer, Session snapshot, node/Skill identity, current actor/project authority, tool grants and frozen Memory context. Handoffs bind the envelope, primary input, instructions and actual request hash. Compaction has its own bounded request allowance and does not produce Memory-use receipts.

After the model returns a response, the Runner persists its delivery confirmation in the existing private spool before sending it. For retrieved Memory, the current context/lease checks, exact versioned use receipts and delivery status commit together. Empty context confirms delivery without creating receipts. Failed model calls remain unconfirmed. Duplicate confirmations return the prior receipt IDs; replay after settlement remains idempotent. Confirmation is an assertion by the authenticated Runner runtime after a Provider response, not independent Provider attestation.

Successful V3 completion requires a confirmed execution handoff and rechecks current context authority. Direct completion also archives delivered Memory dependencies in the cloud Session. Transport failures leave confirmation ahead of completion in the spool; restarting the CLI resends queued work within the valid lease without rerunning the model. This does not recover an unfinished model invocation after process death.

Actual SDK node output exposed a pre-existing hash limitation: the V1 node completion hash rejects floating-point JSON values such as confidence. New nodes use `runner-node-completion-v2` with the Runner JSON hash; V1 hashes remain unchanged.

New handoffs reserve atomically against the existing `run_model_budgets` ledger, shared with cloud SDK work. The same frozen call/token/output/retry limits and explicit price book cover remote execution and compaction. Handoff replay does not reserve again. Delivery adds optional positive input/output usage consistent with its total; missing, malformed, zero-default or older total-only reports retain the conservative reservation. Already-issued pre-budget handoffs retain their old policy. Pricing uses the authenticated Runner's declared actual model ID and explicit server rates; it is an estimate, not a Provider invoice or independent model attestation.

Cost settlement precedes current context delivery checks, so a valid receipt can charge its original attempt after cancellation or source revocation without restoring Memory/Run state. Confirmations record actual over-cap usage, return a safe budget error and prevent successful completion. An offline spool uses the dispatch kind to fail the direct/node lease and withhold queued successful completion after learning of that error. Ordinary transport failure continues to preserve the queue. In-flight, failed or lost remote responses retain their authorized reservation; this adds no unfinished-model checkpoint or automatic process recovery.

Native file tools now require `tool-handoff-v1` in addition to model context handoffs. Before actual IO, the Runner obtains authorization binding its envelope, frozen tool snapshot and hashed arguments/call identity. The cloud rechecks current context, tool grant and model policy and increments the existing shared Run tool counter atomically with the authorization and audit event. Transport replay returns the prior count; each new physical invocation uses a new request ID. Admitted failures remain charged. The cloud never receives raw file paths or bodies. Local reading retains explicit root and credential rules and reads at most 100 KiB plus one byte before refusing oversized files. Clients without the tool protocol receive no native file tools on new claims.

New claims freeze the selected model alias and relevant stored definition fields. Changes block later model/tool admission and successful completion. The first model authorization also pins the Runner's declared actual model ID for the lease, including compaction. This is authenticated runtime reporting, not independent Provider attestation. Already-issued claims lacking these fields retain their prior behavior.

Focused HTTP/SDK checks cover direct delivery, refused premature completion, exact Memory versions, terminal replay, spool reopen, same-device/cross-device nodes sharing a cloud SDK ledger, authorization replay, frozen limits/prices, late usage and offline over-cap refusal. Additional direct SDK checks cover shared tool quota, grant/model revocation between response and IO, replay and model identity switching. Selected existing local budget checks cover concurrent reservation, settlement, retry limits and atomic audit writes after extracting shared transaction operations. No full suite, second Python version, browser or real Provider acceptance was run. Unfinished-run recovery, approvals and complete indirect lineage remain in the main plan.
