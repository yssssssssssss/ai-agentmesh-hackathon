# AgentMesh 界面与记忆操作指南

## 1. 页面地图

登录后，系统默认进入“我的数字人”。当前主导航如下：

| 页面 | 路由 | 主要用途 |
| --- | --- | --- |
| 我的数字人 | `/digital-self` | 查看当前数字人的身份、运行状态、今日活动和个人记忆概览 |
| AI 工作台 | `/workspace` | 对话、执行 Skill、上传文档、搜索可见资料、查看回答来源 |
| 工作洞察 | `/insights` | 查看当前项目的任务、活动、记忆数量和审计事件 |
| 我的知识 | `/knowledge` | 处理 Inbox、查看个人记忆、审核团队候选、查看共享知识和文档 |
| 协作网络 | `/collaboration` | 查看协作任务、Blackboard 时间线、回复、执行锁、交接和协作市场 |
| 管理控制台 | `/admin` | 按账号 capability 管理用户、Agent、Provider、策略和审计 |

“管理控制台”只对具有管理 capability 的账号显示。个人资料和设置以抽屉形式打开，不是独立页面。

## 2. Inbox 是什么

### 2.1 Inbox 不是独立页面

当前界面没有名为“Inbox”的独立导航。Inbox 位于：

```text
我的知识
  → 待我确认
```

页面代码仍使用 Inbox 作为领域名称，界面对用户显示为“待我确认”。

### 2.2 Inbox 的作用

Inbox 是需要人工决定的工作队列。它承接那些不能由 Agent 自动完成或自动越过治理边界的事项，例如：

- 确认 Agent 生成的 Brief；
- 审核疑似提示词注入的外部资料；
- 延后当前暂时不处理的事项；
- 解决普通通知或待办；
- 承接风险审核、高风险工具调用等后端治理事件。

它的核心价值是：

> Agent 可以生成建议和草稿，但涉及共享、风险或正式沉淀时，需要人确认。

### 2.3 Inbox 中可能出现的操作

服务端根据事项类型返回 `allowed_actions`，界面只展示被允许的按钮。

| 事项类型 | 界面操作 | 结果 |
| --- | --- | --- |
| Brief 确认 | 确认并沉淀 | 更新 Brief，并创建团队候选记忆 |
| 普通待办 | 标记已解决 | 将事项设为 resolved |
| 可延后事项 | 稍后处理 | 将事项设为 snoozed，稍后仍可恢复 |
| 提示词注入审核 | 释放内容 | 允许隔离内容继续进入后续流程 |
| 提示词注入审核 | 丢弃内容 | 丢弃隔离证据，不用于回答 |

Brief 和提示词注入审核必须走专用操作，不能直接用“标记已解决”绕过治理流程。

### 2.4 Brief 确认流程

```text
AI 工作台执行 $brief.create
  → 系统生成 Brief 文档
  → Inbox 出现待确认项
  → 我的知识 > 待我确认
  → 点击“确认并沉淀”
  → 核对或修改 Brief 正文
  → 点击“确认 Brief”
  → 文档更新
  → Inbox resolved
  → 创建 team_candidate
```

该操作在服务端使用一个原子事务完成。如果文档已经被其他操作更新，界面会提示状态冲突，并保留用户尚未提交的正文。

## 3. 推荐的日常操作路径

### 路径 A：查看个人工作状态

```text
登录
  → 我的数字人
  → 查看数字人运行状态
  → 查看今日活动
  → 查看短期、项目、归档和团队记忆数量
```

适合每天开始工作时确认：

- 当前绑定的个人 Agent；
- Agent 是否正在处理任务；
- 今天产生了哪些活动；
- 当前项目积累了多少记忆。

### 路径 B：开始一次 AI 工作

```text
AI 工作台
  → 开始新对话
  → 输入自然语言，或点击“选择 Skill”
  → 发送
  → 查看回答
  → 查看 Provider、模型、延迟、降级原因和来源
```

支持的典型 Skill：

| Skill | 用途 |
| --- | --- |
| `$note.save` | 保存私人工作笔记 |
| `$memory.search` | 查询个人、项目和团队经验 |
| `$brief.create` | 生成项目 Brief 草稿 |
| `$research.request` | 使用外部研究 Provider 获取资料 |
| `$data.query` | 查询项目数据指标 |
| `$risk.review` | 发起风险检查 |
| `$system.info` | 查看当前模型和系统配置 |

AI 工作台左侧可以展开历史对话。刷新页面后，Thread、消息、来源和 Provider provenance 仍从服务端恢复。

### 路径 C：保存个人记忆

最直接的界面操作是：

```text
AI 工作台
  → 选择 Skill
  → $note.save
  → 输入要保存的事实、决策或方法
  → 发送
  → 我的知识
  → 个人知识
```

示例：

```text
$note.save 去年 618 沉浸式大图导致首屏核心入口点击下降，最终改为效率型楼层结构。
```

保存后会形成当前用户的 `short_term + private` 记忆。普通闲聊不会自动形成项目记忆。

Research、Data、Risk、Brief 等明确工作流完成后，也会记录“用户请求 + 处理结果 + Thread + Task + Sources”形式的短期个人记忆。

### 路径 D：查询已有记忆

```text
AI 工作台
  → $memory.search 618 首屏入口策略
  → 系统先查已接受团队记忆
  → 再查项目和候选记忆
  → 再查当前用户私有记忆
  → 返回回答和来源
```

如果没有足够结果，系统会创建 Blackboard 求助任务，后续可在“协作网络”查看。

### 路径 E：生成并沉淀 Brief

```text
AI 工作台
  → $brief.create 生成 618 家电会场首屏改版 Brief
  → 我的知识
  → 待我确认
  → 确认并沉淀
  → 修改或核对正文
  → 确认 Brief
  → 团队候选
```

普通用户完成确认后，记忆只进入 `team_candidate + proposed`，不会自动变成正式团队知识。

### 路径 F：审核团队候选

该流程需要 Team Lead、Admin，或被授予 `accept_team_memory` capability 的账号。

```text
使用 Team Lead 登录
  → 我的知识
  → 团队候选
  → 查看候选内容和来源
  → 接受候选
  → 已共享
```

接受后状态变为：

```text
scope = team_accepted
status = accepted
```

项目成员后续执行 `$memory.search` 时，会优先检索这类已审核团队记忆。

### 路径 G：上传和检索文档

```text
AI 工作台
  → 上传文档
  → 查看“文档上传”状态
  → 大文件进入“我的导入任务”
  → 等待完成
  → 搜索可见资料
  → 查看详情
```

上传后的内容会形成：

- 文档记录；
- Source；
- 私有文档摘要记忆；
- 可检索的文档分块。

也可以在：

```text
我的知识
  → 文档
```

查看当前账号可见的文档。

### 路径 H：查看项目状态和记忆变化

```text
工作洞察
  → 当前任务卡片
  → 活动记录
  → 项目记忆
  → 最近审计
```

该页面只显示当前项目的服务端数据，不在前端自行计算业务结论。

### 路径 I：处理协作任务

```text
协作网络
  → 协作中 / 我发起的 / 全部任务
  → 查看协作详情
  → 查看 Blackboard 时间线
  → 回复任务
  → 获取或释放执行锁
  → 填写当前结果和完成条件
  → 交接下一位 Owner
```

按钮由服务端 `allowed_actions` 决定。没有权限的操作不会显示，直接调用接口也会被拒绝。

“协作市场”标签用于：

- 查看市场运行状态；
- 查看发布和发现 Worker；
- 加入或退出市场；
- 查看市场信号。

### 路径 J：管理员检查系统状态

```text
管理控制台
  → 用户管理
  → Agent 配置
  → Provider 与 O2
  → 策略只读
  → 审计日志
```

不同 capability 只开放对应模块。普通用户直接访问 Admin 接口会收到 403。

## 4. 一条完整的记忆演示路径

推荐案例：**“618 家电会场首屏策略从个人经验变成团队资产，并被下一次任务复用。”**

### 第一步：设计师记录私人经验

```text
AI 工作台
  → $note.save 去年 618 沉浸式大图导致入口点击下降，最终改为效率型楼层。
```

验证：

```text
我的知识 > 个人知识
```

出现新的短期私有记忆。

### 第二步：生成正式 Brief

```text
AI 工作台
  → $brief.create 生成 618 家电会场首屏改版 Brief
```

验证：

```text
我的知识 > 待我确认
```

出现 Brief 确认事项。

### 第三步：人工确认

```text
待我确认
  → 确认并沉淀
  → 核对正文
  → 确认 Brief
```

验证：

- Inbox 项消失或变为 resolved；
- Brief 文档版本增加；
- 产生团队候选记忆。

### 第四步：Team Lead 审核

```text
Team Lead 登录
  → 我的知识
  → 团队候选
  → 接受候选
```

验证：

```text
我的知识 > 已共享
```

出现正式团队记忆。

### 第五步：在后续任务中复用

```text
AI 工作台
  → $memory.search 618 首屏入口策略
```

验证：

- 命中已接受团队记忆；
- 回答包含来源；
- Provider 显示 `memory_index`；
- 不创建新的 Blackboard 求助任务；
- 刷新后回答和来源仍存在。

该案例体现了四个核心特点：

1. 个人上下文默认私有；
2. AI 生成内容不能自动进入团队知识；
3. 团队共享需要人工审核；
4. 已审核知识会在下一次任务中被优先复用。

## 5. 当前需要 API 辅助的记忆操作

以下能力后端已经支持，但当前 React 页面没有完整操作按钮：

| 能力 | 接口 |
| --- | --- |
| 手工创建个人记忆 | `POST /api/memory/user` |
| 创建每日总结 | `POST /api/memory/user/daily-summary` |
| 创建项目中期总结 | `POST /api/memory/user/project-summary` |
| 分享个人记忆到项目 | `POST /api/memory/user/{item_id}/share-to-project` |
| 项目长期归档 | `POST /api/memory/user/archive-project` |
| Blackboard 帖子转候选记忆 | `POST /api/blackboard/posts/{post_id}/memory-candidate` |

如果要展示完整的 `short_term → mid_term → long_term` 生命周期，需要在界面演示之外配合 Postman、curl 或测试脚本调用这些接口。

## 6. 角色差异

| 操作 | 普通用户 | Team Lead | Admin |
| --- | --- | --- | --- |
| 使用 AI 工作台 | 是 | 是 | 是 |
| 查看自己的个人记忆 | 是 | 是 | 是 |
| 确认自己的 Brief | 是 | 是 | 是 |
| 查看团队候选 | 否 | 是 | 是 |
| 接受团队候选 | 否 | 是 | 是 |
| 查看已共享团队记忆 | 是 | 是 | 是 |
| 管理用户和全局策略 | 否 | 取决于 capability | 是 |

---

## 7. 当前限制

- 个人 short/mid/long 记忆与团队 candidate/accepted 记忆是两套模型，不要把“项目中期记忆”理解成已经共享的项目知识。
- 个人记忆分享接口目前没有强制检查 `sensitivity`，高敏记忆分享策略仍需加强。
- 普通个人分享和候选接受的审计覆盖不如 Brief 原子确认完整。
- 当前运行边界是单 Workspace、单进程、单 SQLite、可信内网。
- Data API 尚未配置真实业务数据源，数据查询可能显示明确的本地 fallback。
